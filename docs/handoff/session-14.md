## 3. 🆕 S3Gym ③(a) 가 v5 에서 옮겼다 — 그리고 원인을 가를 수 없다

v5 `담김` 10/10 → v6 `이름만` 10/10. v5 대비 바뀐 요소는 **이것 하나** (18/19 같다).

| 원인 후보 | |
|---|---|
| (가) 점수표·슬롯 판정어 제거 | 점수 목표가 요소 판정을 끌던 경로가 사라졌다 (ADR-021 Rationale 3) |
| **(나) v6 가상 예시 수정 — 에이전트가 바꾼 것** | v5 예시의 자기모순(판정어 `없음`, 설명 "이름만")을 고치며 ③(a) 를 **`이름만`** 으로 적었다 — **정성적 정도 표현을 이름만으로 보인 예시**다. S3Gym ③(a) 가 정확히 그 유형이다 |

- **(나) 는 설계 쪽 교란이다.** 사람은 "정성적 크기·방향도 정도다"(v4 설계 §5)로 요소를 인정했는데,
  예시는 정성적 표현이 요약에 들어가면 이름만이라고 가르친다. 두 판단이 **다른 층**(요소 자격 vs 담김
  여부)이라 모순은 아니지만 긴장한다.
- S3Gym 은 v5 · v6 · 손계산이 모두 **3** 인데 **경로가 셋 다 다르다.** v6 는 2.0/4 = r 0.5 **경계**다.
  "점수 일치를 경로 일치로 읽지 말 것"이 v6 에서도 그대로다.

## 4. `prompt_sha256` — 무엇이 바뀌고 무엇이 안 바뀌었나 (D-098)

- **원인:** 이 작업본의 오래된 파일은 `.gitattributes`(`eol=lf`) 이전에 체크아웃돼 **작업본만 CRLF** 다
  (`git ls-files --eol`: 인덱스는 전부 LF). v4·v5·v6 는 LF.
- **eval 쪽**은 LF 정규화 해시 + `prompt_hash_scheme: lf`. 과거 기록은 고치지 않고 대응표로 대조
  (`eval/judge_prompts/README.md`). v4·v5 값은 그대로, v3 `70d7…` → `670f…`, `extract_ontology.v4`
  `9ff5…` → `25b1…`.
- 🔴 **export 계약 해시는 그대로다** — §7.

## 주의 (이월 + 추가)

- 🆕 **완결성 점수를 볼 때 `completeness_scored_by` 부터 본다.** `code`(v6) 와 `judge`(v5 이하)는 직접 비교하지 않는다.
- 🆕 **결정성은 정확성이 아니다.** v6 는 30/30 결정적이고, 손계산과 갈린 두 요소도 10/10 같은 방향이다.
- 🆕 **루브릭 예시를 고치는 것도 판정 기준을 고치는 것이다.** 자기모순 수정이 교란 후보가 됐다.
- 🆕 **요소 파싱 실패는 재시도하지 않고 judge 실패로 센다** (`element_parse_failures`).
- 점수 일치를 판정 경로 일치로 읽지 않는다 — S3Gym 이 v6 에서도 그렇다.
- `finish_reason: length` 면 `stop_kind` 부터. 구조화 출력 필드에 여러 줄 형식을 지시하지 않는다.
- 큰 호출은 소표본 → 결과 보고 → 본 실행 별도 승인.
- handoff 가 들어오면 첫 줄 파일명을 본다. `judge_human_gap` 을 그대로 읽지 않는다 (D-087).
- 측정 전에 `python -m extraction.probe`. 날짜가 바뀌면 다시.
- 실행에 쓰인 프롬프트 버전은 수정하지 않는다 — **v6 가 이번에 그 대상이 됐다.**
- 테스트는 가상환경으로. 실제 Vault·`eval/scores/`·보존소에 쓰지 않는다. 변이 검사는 복사본에서.
