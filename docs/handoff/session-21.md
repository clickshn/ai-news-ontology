## 8. 브레이커 시계 수정 (D-123 · ADR-025 Amendment 2)

**정의 (사용자가 물은 세 가지):**

| 질문 | 답 |
|---|---|
| "게이트 처리에 성공한 실행"이란 | **수집 성공 + 그 실행에 브레이커 없음**(게이트·추출 어느 단계든). 미룬 게이트가 0 일 필요는 없다 — 상한에 걸린 날은 실패가 아니고, 그건 `not_drained` · `evicted` 가 센다. 실행 중간에 브레이커가 걸리면 그 실행 전체를 실패로 본다(앞쪽 소스가 다 돌았는지 요약에서 가를 수 없다 — 이르게 심각이 되는 쪽) |
| 수집 실패와 처리 실패가 동시에 나면 | **시계를 하나로 뒀다.** 세 종류(`source_error` · `env_not_ready` · `breaker`)가 모두 "마지막 정상 처리"부터 잰다. 정상 처리는 성공 수집을 포함하므로 브레이커가 없던 동안은 예전 값과 같다. 둘로 나누면 브레이커 다음 날의 수집 실패가 전날 "성공 수집"부터 재서 같은 결함을 물려받는다 |
| 10/12 재계산 | 실제 실행 요약 두 개를 scratchpad 에 복사해 새 코드로 계산 → 깊이 58.1(가장 최근 성공 수집) − 마지막 정상 처리 90.1시간 전(10/8 14:01) − 24 = **−56.0 · 심각**, 토스트 문구 생성 |

**고친 것:** `pipeline/alerts.py: last_depths` 한 함수 — (마지막 정상 처리 시각, 가장 최근 깊이)를 돌려준다. 사유 문구는 "마지막 성공" → "마지막 정상 처리". `loss_clock` · `severity` · 호출부는 그대로다

**테스트 6건** (`tests/test_schedule.py`): 10/12 재계산(−56.0 · 심각 · 문구) · 상한 미룸은 정상 처리 · 추출 브레이커도 실패 · 공유 시계(동시 발생 + 브레이커 다음 날 수집 실패, 둘 다 48h · −12) · 브레이커 없는 기간은 예전 값과 같음 · **끝-끝**: 4일 공백 뒤 게이트 404 → `breaker|-` 심각 + 토스트. `world` 픽스처에 단계별 클라이언트 동작(`behaviour`)을 받는 한 줄을 넣었다

**변이 4/4** (scratchpad 복사본, 작업본 무관): 예전 시계(브레이커 무시) → 4건 실패 · 깊이를 정상 처리 실행에서 → 3건 · 게이트 브레이커만 실패로 → 1건 · 상한 미룸도 실패로 → 1건

**남은 것:** 브레이커 → 심각 → 토스트 경로는 **테스트로만** 확인했다. 실기는 다음 장애 때 처음 확인된다. 그때 볼 것 — 전달 기록에 `toast: ok` 가 있는지, 사유에 "마지막 정상 처리 N시간 전"이 붙는지
