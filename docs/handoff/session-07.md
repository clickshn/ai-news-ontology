## 2. 🚩 F2 와 같은 결함인데 같은 수정이 아니다

핸드오프가 "복사하지 말라"고 적어 둔 이유가 실제로 셋이었다.

### (1) 타임아웃과 재시도 간격은 **다른 상태를 잰다**

| | 무엇이 일어난 상태인가 | 무엇을 정하는가 |
|---|---|---|
| 타임아웃 | 서버가 **아무것도 주지 않았다** | 한 시도가 소켓을 얼마나 붙잡는가 |
| 재시도 간격 | 서버가 **응답은 했는데 비어 있었다** | arXiv 를 언제 다시 건드리는가 |

"끊고 다시 걸기 vs 기다리기"의 답은 **끊되 곧바로 다시 걸지 않는다**다. 끊는 것은
소켓 점유를 푸는 일이고, 다시 거는 시점은 rate limit 이 따로 정한다. 그래서
**타임아웃도 재시도 슬롯을 소비한다** — 멈춘 arXiv 는 빈 arXiv 보다 나쁜 신호지
좋은 신호가 아니다.

따라오는 결론 하나: **타임아웃을 짧게 잡을수록 재시도가 늘어난다.** 수집기는
재시도가 없어 15초로 잡아도 손해가 없지만 여기는 재시도가 비싼 자리라, 상한을
**더 길게**(30초) 둬야 한다. **F2 값을 복사하면 방향이 반대로 간다** (D-071).

### (2) 🚩 전송을 갈아끼우면 **rate limit 재시도가 rate limit 에서 죽는다**

여기가 제일 조용한 함정이다. arXiv 의 스로틀은 **본문 없는 4xx** 로 오는데,
`feedparser.parse(url)` 은 그걸 빈 피드로 삼켜 줘서 재시도 루프가 받아냈다.
`urlopen` 은 **예외로 올린다.** 그대로 두면 **rate limit 때문에 만든 재시도가
rate limit 이 걸리는 순간 정확히 건너뛰어진다.** 수집기에서는 HTTP 상태가 보이게
된 것이 **의도한 이득**이었는데(D-069), 여기서는 되돌려 넣어야 했다 (D-072).

> **변이 검사가 두 분기의 몫을 갈라 줬다.** 예외 흡수를 통째로 빼면 7건이 깨지지만,
> 전용 `HTTPError` 분기만 빼면 2건만 깨진다 — `HTTPError` 가 `URLError` 의
> 서브클래스라 **재시도 자체는 살아남고**, 잃는 것은 **로그의 상태 코드**다.
> 처음에 "HTTPError 를 흡수해야 재시도가 산다"로 적었는데 측정이 정정했다.
> 재시도를 살리는 것은 `URLError` 계열을 잡는 것 자체이고, 전용 분기는 스로틀(4xx)과
> 회선 장애를 로그에서 구분하는 몫이다.

### (3) 재시도 간격 `(5, 20, 60)` 은 **정책 수치가 아니다 — 그래서 안 건드렸다**

`export/urls.py` 상단 주석이 대는 근거는 "MARA 가 같은 IP 에서 막혔다"는 **실측
관찰**이고, 거기서 간격을 유도한 계산은 없다. 즉 공개 정책에 맞춘 값이 아니라
**넉넉한 쪽으로 임의로 잡은 값**이다. 근거 없는 값을 근거 없이 바꾸는 것이라서
이번 수정에서 **그대로 뒀다.** arXiv 공개 정책과의 대조는 §6 결정 대기로 넘긴다.

## 3. 총 소요 시간 상한 — F2 의 결정 대기와 **같은 질문이 아니다**

session-06 §6 의 "총 시간에도 상한을 걸까"는 **가상의 위협**(조금씩 흘려보내는
서버)에 대한 질문이었다. 여기는 다르다 — 시도 횟수와 간격이 **모두 고정**이라
총합이 **이미 설계로 정해져 있다.**

```
최악 = 4회 × 30초 + (5 + 20 + 60)초 = 205초
```

그래서 **총 예산 파라미터를 새로 만들지 않았다.** 마감 시각을 따로 두면 진실의
출처가 둘이 되고, 어긋나면 어느 쪽이 실제 상한인지 알 수 없다. 필요한 것은 새
파라미터가 아니라 **겪어서 알게 되는 대신 읽어서 알게 하는 것**이라, 최악값을
상수 옆에 적고 재시도·포기를 사유와 함께 로그로 남겼다 (D-073).

> **이 수치는 실측으로 확인됐다.** 작업 도중 기존 테스트 3건이 전송 목을 잃고
> **진짜 arXiv 로 나가면서** 전체 실행이 2분을 넘겼다. 고치기 전이었다면 그 자리가
> 무기한이었다.

### 🚩 재시도 로그가 `sleep` 에 묶여 있었다 (원래 결함, 이번에 같이 고침)

원래 코드는 `if delay:` 안에서 로그를 찍었다. **간격이 0 인 구성에서는 재시도가
조용히 일어난다** — 관측 가능성이 설정값에 달려 있었다는 뜻이다. 로그가 없으면
"느리다"와 "재시도 중이다"가 구분되지 않는다. 시도 횟수(`if i:`)에 걸고 `sleep` 만
간격에 남겼다. 이 결함은 **테스트를 쓰다가** 드러났다 (간격 0 으로 놨더니 로그가 비었다).

### ⚠️ 이 수정이 보장하지 **않는** 것

`fetch_feed_bytes` 의 상한은 여전히 **소켓 연산 1회**짜리라, 조금씩 끝없이
흘려보내는 서버에는 위 산수가 성립하지 않는다. **수집기와 같은 한계**이고 미해결이다.
다만 전송이 한 곳으로 합쳐졌으므로 **고칠 자리도 한 곳**이 됐다 (§6).

## 4. 설계 판단 — 왜 이렇게 했나

**ADR 을 남기지 않았다.** session-06 과 같은 계산이다 — 새 의존성 0개, 데이터
형식·식별자 불변, 외부 서비스 선택 아님. 유일하게 걸릴 만한 것이 **전송 공유**인데,
`export → collectors` 의존 방향은 종전 그대로이고(이미 `strip_html`·`BODY_MAX_CHARS`
를 가져온다) 되돌리기는 15줄을 다시 복사하는 일이다. D-071~073 으로 남겼다.
**다른 판단이었으면 `adr-skill:adr-recorder` 로 갔어야 한다** (F12).

- **전송을 복사하지 않고 공유했다** (D-072). 복사하면 상한·크기 제한·slow-drip
  한계가 **두 벌**이 되고, 다음에 고칠 때 한쪽만 고쳐진다.
- **UA 는 합치지 않았다.** 피드 수집과 계약 export 는 **다른 클라이언트**이고
  arXiv 는 식별 가능한 UA 를 요구한다. **전송이 하나여도 신원은 둘이다.**
  session-06 §6 의 "`USER_AGENT` 가 두 곳에 생겼다"에 대한 답이 이것이다.
- **재시도 정책은 공유하지 않았다.** 수집기는 재시도가 없고 여기는 있다 —
  같은 함수에 넣으면 한쪽의 판단이 다른 쪽에 조용히 흘러간다.
- **타임아웃을 `config.yaml` 에 올리지 않았다.** D-070 과 같은 이유이고, 함수
  인자로 열어 둬야 테스트가 0.4~0.5초로 낮춰 **실제로 끊기는지**를 잰다.
- **`ARXIV_RETRY_DELAYS_S` 를 건드리지 않았다.** 위 §2-(3).

## 7. 커버리지 — 변이 검사로 무엇이 실제로 잡히는지 확인했다

| 변이 | 실패 |
|---|---|
| `timeout` 을 전달하지 않고 5초 고정 | 3건 |
| **예외를 전혀 흡수하지 않는다** (F2 수정을 문자 그대로 복사) | **7건** |
| 전용 `HTTPError` 분기만 제거 | 2건 (재시도가 아니라 **로그의 상태 코드**를 잃는다 — §2) |
| 타임아웃이 재시도 슬롯을 소비하지 않는다 | 1건 |
| 재시도 로그를 다시 `sleep` 에 묶는다 | 3건 |
| arXiv UA 를 안 붙인다 (수집기 UA 로 나간다) | 1건 |
| `ARXIV_FETCH_TIMEOUT_S` 를 15초로 (F2 값 복사) | 1건 |
| 포기 로그 제거 | 3건 |
| 빈 Content-Type 을 무조건 넘긴다 | **0건 — 의도한 결과** (아래) |
| 복원 후 | **16/16 통과** |

> **한 건이 살아남았고, 그건 테스트 공백이 아니라 주장이 과했던 것이다.**
> 수집기에서는 빈 Content-Type 이 `bozo` 를 세워 정상 응답을 파싱 실패로 만들었지만
> (session-06 §3), `export/urls.py` 는 **`bozo` 로 분기하지 않고 `entries` 만 본다.**
> 그래서 그 가드는 지금 아무것도 막고 있지 않다. 가드는 남기되(나중에 bozo 분기가
> 생기면 이미 옳다) **주석과 테스트 독스트링을 측정에 맞게 낮췄다.** 살아남은 변이를
> 없애려고 없는 계약을 만들지 않는다.

| 축 | 테스트 |
