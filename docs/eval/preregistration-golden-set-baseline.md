## 1. 이 실행이 세우는 것과 세우지 않는 것

**세운다:** "오늘 이 파이프라인(v4 + gemma)을 골든셋에 돌리면 나오는 값."
다음 실행이 여기서 얼마나 움직였는지 재는 회귀 기준점이다.

**세우지 않는다:** "v4 프롬프트의 성능." 모델을 고정하려면 Opus 가 필요하고,
그건 승인 대상이 아니라 게이트 1번의 답이 "아니오"가 되는 행위다 (§6).

### 🔴 과거 Opus 값과의 차이를 계산하지 않는다

산출물에 **과거 Opus 값과의 차이 칸을 만들지 않는다.** 만들면 아래 세 교란이
그 숫자 안에 숨는다.

| # | 교란 | 영향 범위 |
|---|---|---|
| ① | **과거 Opus 예측이 디스크에 없다** — `eval/scores/` 는 비어 있고(gitignore), 골든셋 3건의 URL 은 `data/extractions/`·`data/replays/main/` 어디에도 없다 | **전 항목.** 요약 원본은 아예 없어 judge 축은 비교 불가. 필드 축은 `eval/README.md` 집계표에서 부분 역산만 된다 (Jaccard 0.5 는 여러 집합이 가능) |
| ② | **judge 모델도 바뀌었다** — `eval.judge_model: gemma-4-31B-it`. 과거 점수는 전부 Opus judge 가 매겼다 | 요약 3축 전부. 후보 교체와 채점자 교체가 같은 숫자에 섞인다 |
| ③ | **프롬프트도 같이 바뀐 항목이 2건** — #33001·S3Gym 은 v3 → v4 | 3건 중 2건. #33003 만 v4 → v4 |

> ③ 은 셋 중 **가장 약한 제약이다.** ①이 이미 비교 자체를 막는다.

### 재추출이 고치지 못하는 비대칭 (판정에 넣지 않고 기록만)

- **골든셋 `expected` 3건이 전부 Opus 드래프트를 사람이 수정한 것이다.**
  gemma 를 이 라벨에 대고 채점하는 것은 구조적으로 Opus 에 유리한 출발점이고,
  재추출로 사라지지 않는다. 임계값을 뒤집을 크기인지는 모른다.
- **#33001 은 `labeling_guideline: pre-2026-08-30`** 이고, 영향도 근거에 루브릭
  밖 기준("AI 엔지니어링 직무 관련성")이 섞여 있다 (D-046). 사후 수정하지 않는다.

### 골든셋이 프롬프트 입력을 전부 보존하지 않는다

`build_variables()` 는 `source_name`·`published_at` 을 프롬프트에 넣는데 골든셋
파일에는 없다. **유도값을 쓰고, 산출물에 유도값임을 명시한다.**

| 항목 | `source_name` | `published_at` | 근거 |
|---|---|---|---|
| #33001 | `GeekNews` | 2026-08-29 | `config.yaml` sources · 골든셋 id |
| #33003 | `GeekNews` | 2026-08-29 | 〃 |
| S3Gym | `arXiv cs.CL (Atom API)` | 2026-08-31 | 〃 |

**따라서 #33003 의 "단일 변수(모델만 교체)"도 이 두 필드가 원래 실행과 같았다는
가정 위에서만 성립한다.** 가정이므로 결론에 쓰지 않는다.

## 2. 기록할 항목 (실행 전 고정)

### 2.1 대조축 — 결정적, 호출 없음

- 항목 3건 × 필드별 점수: `기술영역`(Jaccard) · `발표유형`(정확일치) ·
  `영향도`(정확=1.0, ±1=0.5) · `관련기업` · `관련기존기술`
- `field_accuracy` 집계 — 임계값 0.90 과의 거리
- **`기록만` 필드(`관련기업`·`관련기존기술`)는 집계에 넣지 않는다.** 정답이 빈
  목록일 때 Jaccard 가 0 이 되는 사례(#33003 `관련기존기술`)를 "많이 틀렸다"로
  읽지 않는다 (D-060)

### 2.2 추출 실행 제원

- `prompt_sha256`, 모델 id, `temperature`, `max_tokens`
- **스키마 실패를 세 갈래로 나눠 적는다** — 문법 밖(구조상 불가능 = 강제가 꺼진
  것) / 수량 제약 위반(모델·프롬프트) / 절단(`finish_reason == "length"`, 디코딩
  설정). 섞으면 수치가 모델이 아닌 것을 잰다 (ADR-018)
- 재시도 횟수, 지연, 토큰
- `omitted_vendor_params` — 설정에 남은 벤더 전용 파라미터(`effort: high`,
  `thinking: adaptive`)가 보내지지 않았음을 명시 (D-080)

### 2.3 judge 축 — **항목당 5회 반복**

- 3축(충실성·완결성·간결성) × 3항목 × 5회
- **축별 분포: 평균 · 표준편차 · 최빈값 · 범위**
- `judge_human_gap` 을 **축별로** 기록한다. 종합값만 읽으면 상쇄가 숨는다 —
  #33001 은 종합 0.000 인데 축별로는 충실성 −1 · 완결성 +1 이었고(D-054),
  #33003 은 축이 하나만 어긋났는데 종합이 +0.334 였다 (D-060)
- 완결성 4슬롯 판정(①사건 ②범위 ③정도 ④경위)과 `slot_adherence`
- judge 호출 실패 건수와 사유. **실패해도 대조 결과는 남는다** (설계대로)

## 3. 🔒 판정 기준 — 데이터 보기 전에 고정

### 3.1 judge 결정성

`gemma-4-31B-it` 는 `temperature: 0` 을 **받는다.** Opus 5 는 400 으로 거부했다
(D-033) — 그래서 D-042 의 "judge 는 결정적이지 않다"는 전제가 모델 교체로 바뀌었을
수 있다. 흔들림 폭을 모른 채 1회값으로 기준선을 세우면 **이후 비교에서 변화와
노이즈를 구분할 수 없다.**

| 결과 | 판정 | 기준선을 어떻게 기록하나 |
|---|---|---|
| **3축 전부 5/5 회 동일** | gemma judge 는 이 구성에서 **결정적** | 기준선은 **1회값**으로 충분. 이후 비교는 단일값 대 단일값 |
| **어느 축이든 변동** | 그 축은 **비결정적** | 그 축의 기준선은 **분포**(평균·sd·최빈값·범위)로 기록. 이후 비교는 **분포 기준**으로 하고, 범위 안의 차이를 변화로 읽지 않는다 |

- 축마다 따로 판정한다. **한 축이 흔들렸다고 나머지를 비결정으로 내리지 않는다** —
  D-049 가 "비결정성은 축마다 다르다"를 이미 관측했다(완결성·충실성 변동 0,
  간결성만 8회 중 2회).
- 판정 단위는 **항목별 축**이다. 3항목 중 하나만 흔들린 축은 "그 축이 흔들린다"로
  기록하고 항목을 명시한다.
- **5/5 동일이 "judge 가 옳다"는 뜻이 아니다.** 같은 답을 다섯 번 낸 것과 맞는
  답을 낸 것은 다르다. 이 판정은 재현성만 잰다.

### 3.2 임계값

`config.yaml: eval.thresholds` 의 값을 **그대로 쓴다.**

- `field_accuracy ≥ 0.90`
- `summary_faithfulness ≥ 4.0`

**데이터를 본 뒤에 바꾸지 않는다.** 바꾸고 싶어진 이유는 실행 기록의 "다음 사전
등록의 입력" 절에 적는다 (D-065 와 같은 처리).

### 3.3 미달을 실패로 읽지 않는 자리

골든셋 3건 = 채점 슬롯 9개이므로 **필드 1개의 최대 영향이 0.111** 인데 임계값까지
거리가 **0.048** 이다 (D-060). 한 필드만 만점이 돼도 판정이 뒤집힌다. 따라서
`field_accuracy` 의 통과/미달은 **모델 품질의 결론이 아니라 기준선 수치**로만
기록한다.

| # | 단계 | 호출 | 중단 조건 |

>
> probe 설계는 **"JSON 을 쓰지 마라"** 다. "스키마를 어겨 보라"로 짜면 모델의
> 순종도와 디코더의 강제가 섞여 정반대 결론이 나온다 (session-03 의 첫 probe).

## 5. 산출물을 만드는 방법

**신규 모듈 `eval/predict.py`.** 골든셋 `input` → `RawItem` 복원 →
`extract_ontology` → `{item_id, ontology}` JSONL.

**골든셋 3건을 `data/extractions/` 보존소에 넣고 `export/replay.py` 를 쓰지
않는다.** 보존소는 export 코퍼스의 입력이고 MARA 가 그 산출물을 읽는다. 측정용
항목이 거기 섞이면 코퍼스로 흘러든다.

원본 응답은 `raw/` 아래에 **변환 전에** 내린다 (D-052). 토큰 비용이 0 이어도
같다 — 규칙을 비용으로 정당화하면 비용이 0 인 곳에서 규칙이 사라진다.

### 벤더 arm(v4+Opus)을 만들지 않은 이유

2단계(Opus 로 먼저 맞춘 뒤 gemma 로 교체)는 게이트 1번의 답이 **"아니오"**가 되어
승인 대상이 아니라 규칙 위반이다. 2~6번은 전부 답할 수 있다 — 데이터는 공개
자료고, 모델은 `claude-opus-5`, 건수 6건, 비용 약 $0.35 (session-01 실측 건당
$0.0686 · D-060 judge 3건 $0.1613 기준).

**2~6번이 깔끔하게 통과한다는 것이 정확히 ADR-017 의 모양이다.** 크기를 재는
항목은 다 맞고 가부 항목 하나만 아니오다. 비용이 작다는 사실을 1번의 답으로
쓰지 않는다. D-065 가 같은 판단을 이미 했다 — *"만들려면 벤더 호출이 필요한데
그게 이 작업이 없애려는 행위다."*

Opus arm 이 필요해지면 그것은 세션 단위 승인이 아니라 **ADR-018 전제의
재개방**이고, MARA ADR-021 과의 관계 재판단과 `pip install -e .[vendor]` →
`config.yaml` 순서의 롤백이 딸려 온다 (ADR-020 Reversibility).
