# 설계 — 완결성 루브릭 v6: judge 는 요소 판정만, 슬롯·점수는 코드가

- **작성:** session-14 (2026-09-29)
- **대상:** `eval/judge_prompts/summary_quality.v6.md`, `eval/completeness.py`, `eval/runner.py`
- **결정:** ADR-021 · 결정 로그 D-097 (v6) · D-098 (해시) · D-099 (`--item`)
- **검증:** `docs/eval/preregistration-rubric-v6.md` — **이 문서만으로 v6 가 낫다고 말하지
  않는다.** 대조군과 함께 반복 채점하기 전까지 미검증이다
- **앞선 설계:** `docs/eval/rubric-v4-design.md` — 라벨(`completeness_slots`)·요소 판정 정의·
  점수표는 거기서 정했고 **그대로 쓴다.** 여기서 바뀌는 것은 **누가 계산하는가** 하나다

---

## 1. 무엇을 고치나

v5 는 judge 에게 세 단계를 맡겼다.

| 단계 | 성격 | v5 에서 |
|---|---|---|
| ① 요소 판정 — 담김 / 이름만 / 없음 | **판단** | judge |
| ② 슬롯 판정 — 요소 판정에서 충족 / 부분 / 미충족 | **계산** (루브릭의 표) | judge |
| ③ 점수 — 슬롯 판정에 점수표 | **계산** | judge |

②·③ 은 ① 의 결정적 함수인데 judge 가 했고, **②에서 규칙을 어겼다** (run-log-session-13 §4):

| | 요소 판정 (judge) | 슬롯 판정 (judge) | 규칙대로 | judge 점수 | 요소대로 계산 |
|---|---|---|---|---|---|
| #33001 ② | `(a) 이름만` | 부분 | **미충족** | 3 | **2** |
| S3Gym ④ | `(a) 없음 / (b) 이름만` | 부분 | **미충족** | 3 | 3 |

둘 다 10/10 같은 모양 — **"이름만은 담김으로 세지 않는다"를 요소 단계에서는 지키고 슬롯
단계에서 놓는다.** 사전 등록 지표는 #33001 을 통과로, S3Gym 을 "표 미준수"로 읽었다.

**v6 는 ②·③ 을 코드로 옮긴다.** 그러면 이 이탈은 구조상 나올 수 없고, 그 이탈을 재던
과정 지표(v5 H5)는 **대상이 사라진다.**

### 호출 0건 재계산 — v5 의 요소 판정에 v6 계산을 적용하면

v5 본 실행(`20260929T000543Z`) 30회의 요소 판정을 `eval.completeness` 로 다시 계산했다.

| 항목 | v5 judge 점수 | v5 요소 판정 → 코드 계산 | 요소 판정 모양 |
|---|---|---|---|
| #33001 | `{3:10}` | `{2:10}` | 1가지 (10/10 같다) |
| #33003 | `{3:10}` | `{3:10}` | 1가지 |
| S3Gym | `{3:10}` | `{3:10}` | 1가지 |

⚠️ **이것은 v6 의 예측이 아니다.** v6 는 judge 에게 슬롯 판정어와 점수표를 보이지 않는다.
프롬프트가 달라지면 요소 판정도 달라질 수 있다 — 그것이 사전 등록의 관찰 O1 이다.

## 2. 설계

### judge 가 내는 것 — 요소 판정만, 한 줄

`①사건: (a) 담김 | ②범위: (a) 이름만 (…) | ③정도: (a) 담김 / (b) 없음 / (c) 없음 | ④경위: (a) 없음 / (b) 없음`

- **v5 의 한 줄 형식을 유지한다** (D-094). 여러 줄 형식 지시가 v4 퇴화의 유력한 원인이었다.
- 슬롯 판정어(충족/부분/미충족), `→ 합계 / 분모 / 점수` 를 **쓰지 않는다.** 루브릭에서 점수표
  자체를 뺐다 — judge 가 원하는 점수에 맞춰 요소 판정을 고를 경로를 줄인다.
- 요소 판정 정의(담김/이름만/없음)와 충실성·간결성 본문은 v5 와 **글자 그대로 같다**
  (`tests/test_eval_rubric_v6.py::test_v6_keeps_v5_text_where_it_should`).

### 출력 모델 — v6 에만 따로 (`ElementJudgement`)

완결성 칸이 `{rationale}` 뿐이고 **score 가 없다.** 점수 칸을 두고 무시하는 안은 택하지 않았다:
judge 가 점수를 적으면 원본에 "judge 가 낸 점수"가 남아 어느 쪽이 기록인지 흐려지고, 점수를
먼저 정하는 경로가 그대로 남는다.

**`SummaryJudgement` 는 고치지 않았다** — v3 대조군이 structured output 으로 쓰는 스키마다
(D-090). v6 만 다른 디코딩 제약에서 돈다. v6 의 비교 상대는 v5 가 아니라 **같은 날의 v3** 이다.

어느 루브릭이 코드 계산인지는 **이름으로 명시한다** (`eval.runner.CODE_SCORED_RUBRICS`).
프롬프트 내용에서 추론하면, 추론이 틀렸을 때 v5 가 조용히 코드 계산으로 돌거나 그 반대가 되고
어느 쪽이든 점수는 멀쩡히 나온다.

### 파서 — 엄격하게, 기본값 없이 (`eval/completeness.py`)

| 경우 | 처리 |
|---|---|
| 라벨의 요소 표기 (a)(b)… 와 읽힌 표기 집합이 **정확히 같다** | 읽는다 |
| 빠진 요소 / 라벨에 없는 표기 | **실패** |
| 같은 요소에 판정이 둘 (서로 다름) | **실패** |
| 같은 슬롯 표기(①~④)가 두 번 | **실패** — 어느 쪽이 판정인지 모른다 |
| 요소가 있는 슬롯의 표기가 없다 | **실패** |
| 분모 제외 슬롯 | 읽지 않는다 (표기가 없어도 된다) |

- **실패는 judge 실패로 기록한다** (`judge 실패: 요소 판정 파싱: …`). 점수를 내지 않는다.
  빠진 요소를 `없음` 으로 채우면 **형식 실패가 낮은 점수로 둔갑한다** — 실패율 대신 점수
  분포가 움직이고, 원인을 가를 수 없다.
- **재시도하지 않는다.** 파싱은 structured output 검증 뒤에 일어나므로 클라이언트 재시도에
  걸리지 않는다. 걸리게 하려면 항목마다 다른 동적 출력 모델이 필요하고, 그러면 실패가
  재시도 뒤로 숨는다. 실패는 실패율로 보이게 둔다.
- v4/v5 사후 관찰 파서(`eval.analysis.element_verdicts`)와 **다른 함수다.** 그쪽은 읽히는
  만큼만 읽고 200자 창으로 자른다. 이쪽은 점수의 입력이라 창이 없다.
- 분모는 **라벨에서** 센다. judge 는 분모를 적지 않는다.

**판정 규칙의 정본이 한 곳이 됐다.** `state_from_elements`·`completeness_from_states` 는
`eval/analysis.py` 에서 `eval/completeness.py` 로 옮겼고 analysis 는 그것을 가져다 쓴다 —
v5 를 재는 잣대와 v6 가 계산하는 규칙이 갈라지지 않는다.

### 기록 — 점수의 출처를 행마다

| 필드 | 값 |
|---|---|
| `ItemScore.completeness_scored_by` | `code` (v6) / `judge` (v5 이하) / None (호출 안 함·실패). **이 필드가 없던 기록은 judge 다** |
| `ItemScore.completeness_computation` | 요소 판정 · 슬롯 판정 · 합계 · 분모 · 점수 |
| `judgement.completeness.score` | v6 에서는 **코드 계산값.** `rationale` 은 judge 원문 |
| `RepeatStats.completeness_scored_by` | `code` / `judge` / `mixed` |
| `RepeatStats.element_parse_failures` | 파싱 실패 회차 (`failures` 에 포함) |

**코드 계산 행에서는 판정어를 읽는 과정 지표를 `None` 으로 둔다** — `state_adherence`,
`score_table_adherence`, `element_slot_consistency`, `denominator_adherence`, `slot_adherence`.
v6 근거에는 판정어가 없으니 그대로 돌리면 0 이 나오고, 구조상 성립하는 값을 1.0 으로 적으면
"쟀다"로 읽힌다(`judge_human_gap` 이 숫자로 나와 살아 있는 것처럼 보였던 것과 같은 모양, D-087).
슬롯·요소 판정 도수(`slot_state_counts`·`element_verdict_counts`)는 계산 경로에서 센다.

## 3. 🔴 기록되는 점수의 뜻이 바뀐다 (ADR-021)

| | v3 | v4 / v5 | **v6** |
|---|---|---|---|
| 무엇이 핵심인가 | judge | 사람 (라벨) | 사람 (라벨) |
| 요소가 요약에 있는가 | judge | judge | **judge** |
| 슬롯 판정·점수 | judge | judge | **코드** |
| 기록되는 점수 | judge 의 완결성 판단 | 라벨 대비 커버리지 (judge 가 계산) | **judge 의 요소 판정으로 코드가 계산한 라벨 대비 커버리지** |

- **v5 3점과 v6 2점을 "요약이 나빠졌다"로 읽지 않는다.** 같은 요약이다 (예측 파일 해시 동일).
- 추이는 **v6 기준선부터** 다시 센다. 결과 파일에서 `completeness_scored_by` 가 다른 행을
  한 평균에 넣지 않는다 (`summarize` 가 note 를 남긴다).

## 4. 🔴 v6 가 없애지 않는 것 — "그것이 요약에 있는가"

**요소 판정은 여전히 judge 판단이다.** v6 가 없애는 것은 **그 뒤의 계산**이고, 판단의
비결정성·편향은 그대로다.

v5 에서 그 판단은 흔들리지 않았다(30/30 결정적). 대신 **한쪽으로 기울 수 있다는 것**을
#33001 ②(a) 가 보였다:

| | |
|---|---|
| 요소 (라벨) | 신뢰할 수 없는 입력(.vpk 파일·스트림)을 여는 FFmpeg 연동 애플리케이션 |
| 요약 | "FFmpeg의 Sony PS2 VPK 디먹서에서 … 악성 .vpk 파일을 여는 애플리케이션이 충돌하여 …" |
| judge (v5, 10/10) | **이름만** — "'신뢰할 수 없는 입력'이나 'FFmpeg 연동'이라는 구체적 범위가 누락됨" |
| 에이전트 손계산 | 담김 |

어느 쪽이 옳은지는 측정이 가르지 않는다. 요소가 두 사실("신뢰할 수 없는 입력" · "FFmpeg 연동
애플리케이션")을 합친 **복합 요소**일 수 있다 — 라벨 수정은 사람의 몫이다 (D-039, handoff 결정 대기).

**v6 에서 이 기울기는 더 위험해진다.** v5 에서는 judge 가 슬롯 단계에서 이름만을 부분으로 올려
**우연히** 손계산과 같은 3점이 나왔다. v6 에서는 계산이 규칙대로 되므로 그 요소 판정이 **그대로
2점으로 박힌다** — 흔들림이 없으니 눈에 띄지 않는다. 결정성이 곧 정확성이 아니다.

## 5. 같이 처리한 것

### `prompt_sha256` 을 줄바꿈과 무관하게 (D-098)

`eval.runner.prompt_sha256` 이 **CRLF → LF 로 맞춘 뒤** 해시한다. 결과 행에
`metadata.prompt_hash_scheme = "lf"` 를 남긴다 (`eval/predict.py` 행·메타에도).

- **왜:** 원시 바이트를 세던 때는 같은 커밋이 체크아웃마다 다른 값을 냈다. 이 작업본은
  `.gitattributes`(`eol=lf`)가 생기기 전에 체크아웃된 파일이 CRLF 로 남아 있다
  (`git ls-files --eol`: 인덱스는 전부 LF). 모델이 받는 텍스트는 같다 — `read_text` 가 정규화한다.
- **이미 기록된 해시는 다시 쓰지 않는다.** 결과 파일은 그 시점의 기록이다. 대신
  `eval/judge_prompts/README.md` 에 **대응표**를 둔다. LF 로 체크아웃된 파일(v4·v5)은 두 방식의
  값이 같아 끊기지 않는다. 끊기는 것은 CRLF 작업본에서 기록된 값뿐이다 (v3 `70d7…` → `670f…`,
  `extract_ontology.v4` `9ff5…` → `25b1…`).
- ⚠️ **`export/runner.py: prompt_sha256` 은 바꾸지 않았다.** 그 값은 MARA 출력 계약 §12.2-3 의
  provenance 다. 보존소 30건의 `9ff5a9d3…` 은 **CRLF 작업본의 값이라 LF 클론에서는 재현되지
  않는다** — 계약이 "MARA 쪽에서 파일만 받아 같은 값을 재현"하려는 것이면 지금 깨져 있다.
  계약 문서를 먼저 고쳐야 하는 일이라 handoff 결정 대기로 넘긴다.

### `eval.runner --item` (D-099)

`--item ID` (여러 번). 골든셋 순서를 유지하고, **없는 ID 가 하나라도 있으면 judge 클라이언트를
만들기 전에 멈춘다.** session-13 진단은 골든셋 사본 디렉터리로 우회했다.
