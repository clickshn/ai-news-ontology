## 2. ① 통제어휘 이탈률 — **판별력이 없다. 0%는 모델이 아니라 디코더를 잰 값이다**

🚩 **이것이 이 실행에서 가장 중요한 기록이다.**

- **측정:** 사전 등록 §3① 이 지정한 대로 MARA `src/tools/contract_import.py` 의
  `validate_record` 로 대조했다. **새 판정기를 만들지 않았다.**
  이 레포의 `export/conformance.py: check_10_vocab` 으로도 같이 돌려 둘 다 통과.
  - MARA `validate_record` 위반 **0건** / 생산자 `check_10_vocab` **PASS**
  - manifest: `tech_domain` 14종 / `release_type` 8종 /
    `vocab_version = config=1;schema_sha256=2b42e09b…`
  - MARA 레포는 **읽기만 했다.** 코드를 읽어 돌렸을 뿐 한 바이트도 쓰지 않았다.

**그런데 0%는 gemma 가 어휘를 잘 지켰다는 뜻이 아니다.**

> `response_format={"type":"json_schema"}` 의 enum 제약이 **디코딩 단계에서 강제된다.**
> 실측으로 확인했다 — `enum:["빨강","파랑"]` 스키마에 `색=초록` 을 지시했더니
> `"빨강"` 이 나왔다. **목록 밖 값은 생성 자체가 불가능하다.**
> Opus 5 쪽도 SDK structured outputs 로 같은 상태였고, 그래서 기준선도 0% 였다.

즉 **①은 양쪽 다 0%가 구조적으로 보장되며, 합격/불합격을 가르는 힘이 없다.**
이 지표가 실제로 잰 것은 모델의 어휘 준수가 아니라 **디코더가 어기게 놔두지 않았다는
사실**이다.

**사전 등록 §2.1-2 가 걱정한 것이 실제로 일어난 사례로 기록한다** — *"강제 수준이
다르면 §3-(2)의 수치가 모델 능력이 아니라 디코딩 설정을 재게 된다."* 강제 수준이
**달라서** 문제가 된 것이 아니라, **양쪽 다 강해서** 지표가 포화된 경우다.

⚠️ **그래서 합격/불합격은 실질적으로 ②가 갈랐다.** ①은 통과했지만 정보를 주지 않았다.
①을 계속 쓰려면 강제가 닿지 않는 층(자유 필드 표기, 라벨 정확도)으로 옮기거나,
강제를 끄고 재는 별도 실행이 필요하다. **이 판단은 다음 사전 등록에서 한다 —
데이터를 본 뒤에 지표를 바꾸지 않는다.**

## 3. ② structured output 실패율 — **0%. 다만 실패를 한 칸에 넣지 않았다**

30건 전부 1회 시도에 pydantic 검증을 통과했다. `SchemaMismatchError` 0건.

강제가 켜져 있으면 실패가 세 갈래로 갈리고, 섞으면 수치가 모델이 아닌 것을 잰다.
**사전 등록 §3② 의 정의와 10% 임계값은 그대로 쓰고, 내역을 덧붙여 적는다.**

| 갈래 | 뜻 | 이번 실행 |
|---|---|---|
| (i) 문법 밖 출력 | 강제가 걸린 동안 **구조상 불가능.** 나오면 모델 실패가 아니라 **강제가 꺼진 것** | 0건 |
| (ii) 수량 제약 위반 (pydantic 거부) | ②의 본체. 모델 능력 / 프롬프트 | 0건 |
| (iii) 절단 (`finish_reason == "length"`) | **디코딩 설정**(`max_tokens`)이지 모델 능력이 아니다 | 0건 |

`export/replay.py` 가 건별로 `finish_reasons` 를 남긴다.

### ⚠️ Opus 기준선의 비대칭 — **해소되지 않는다**

사전 등록 §3② 이 스스로 경고한 항목이다.

> *"생산자 session-01 에 실패 기록이 없다 → 0건으로 본다. **'기록이 없다'와 '0이었다'는
> 다르다.** 이전 실행 시 양쪽 모두 실패 카운터를 남긴다."*

**양쪽 중 한쪽만 남겼다.** vLLM 쪽은 건별 카운터가 있지만, Opus 실행은 이미 지나갔고
다시 돌리는 것은 벤더 호출이라 **할 수 없다.** 따라서 ②의 비교는

    vLLM 0% (실측)  vs  Opus 0% (**가정**)

이고, 이 비대칭은 **이번 판정에서 해소 불가**다. 실무적으로는 0% ≤ 10% 라 기준선이
무엇이든 합격이지만, *"두 수치가 같은 종류의 근거를 갖고 있다"* 고 읽으면 안 된다.

## 4. ③ judge 점수 — **측정하지 않았다. 보류 근거를 적는다**

자기 선호 편향(judge=후보=`gemma-4-31B-it`)은 사전 등록이 이미 알고 적은 문제이고,
**그것만이라면 참고값으로 기록할 수 있었다.** 보류를 결정한 것은 다른 이유다.

> 🔴 **Opus 5 측 골든셋 예측이 레포에 없다. 그래서 "차이"를 계산할 수 없다.**

- 사전 등록 §3③ 이 재라고 한 것은 절대값이 아니라 **Opus 산출물과의 차이(≤ 0.5)** 다.
- 골든셋 3건(`#33001`, `#33003`, S3Gym)의 URL 은 재추출 30건 **어디에도 없고**,
  `eval/scores/` 는 비어 있다. Opus 가 이 3건을 추출한 결과가 남아 있지 않다.
- Opus 예측을 새로 만들려면 **벤더 호출**이 필요하다. 그것이 이 이전 작업이 없애려는
  바로 그 행위다.

**비교 대상 없는 절대값은 참고값도 되지 못한다.** gemma judge 가 gemma 요약에 4.2를
줬다고 해서 그 수치가 무엇과 비교돼 어느 방향인지 말할 수 없고, 자기 선호 편향이
얹히면 해석 가능한 성분이 남지 않는다. 그래서 **호출을 하지 않았다** — 쓸 수 없는
수치를 만들어 결과 문서에 얹으면 다음 사람이 그걸 근거로 쓴다.

**judge 대조는 Opus 예측이 확보되면 별도로 판단한다.** 그때까지 ③은 공란이고,
사전 등록 §3.1 대로 **③의 부재가 불합격을 만들지 않는다.**

> 다만 `eval.judge_model` 자체는 이번에 `gemma-4-31B-it` 으로 **이전했다.**
> 측정을 안 한 것과 벤더를 계속 가리키는 것은 다르다 — 후자는 전제 위반이다.

## 5. 대조 성립 조건 (사전 등록 §2.1) — 3 충족 / 1 조건부

| # | 조건 | 판정 |
|---|---|---|
| 1 | 프롬프트를 한 글자도 바꾸지 않고 돌릴 수 있는가 | ✅ `extract_ontology.v4.md` 무변경. **system 역할을 네이티브로 받아** 전달 형태도 안 바뀌었다 (gemma 계열이 흔히 거부하는 지점) |
| 2 | structured output 을 같은 강도로 걸 수 있는가 | ⚠️ **조건부.** 계열은 같다(서버 문법 강제 + 클라이언트 검증). 다른 점 두 가지 → 아래 |
| 3 | 재시도 정책이 같은가 | ✅ 설계로 맞췄다. 오류 되먹여 1회 재시도 → `SchemaMismatchError(attempts=2)`. 되먹이는 문구까지 같다 |
| 4 | `prompt_sha256` 이 달라지는가 | ✅ 변화 없음. 보존된 30건 전부와 일치 |

**2번의 차이 두 가지:**

1. 벤더는 SDK(`messages.parse(output_format=…)`)가 **강제와 검증을 함께** 한다.
   여기서는 강제(vLLM)와 검증(우리 pydantic)이 **분리**돼 있다.
2. 🔴 **이 엔드포인트는 모르는 파라미터를 400 이 아니라 조용히 무시한다.**
   `guided_json` 으로 썼으면 이번 측정 전체가 "강제 없는 gemma"를 잰 것이 되고,
   **알 방법이 없었다.** 상세와 판별 방법은 **ADR-019** / `.claude/rules/vllm-endpoint.md`.

### 그 밖에 바뀐 것 — 파라미터

"모델만 바꿨다"가 정확하지 않다. 대응 파라미터가 없어서 함께 바뀐 것이 있다.

| | Opus 5 | gemma-4-31B-it |
|---|---|---|
| `temperature` | **보내지 못함** (400, deprecated) | **0** |
| `output_config.effort` | `high` | 대응 파라미터 없음 |
| `thinking` | `adaptive` | 대응 개념 없음 |

`temperature=0` 은 게이트와 같은 이유로 골랐다(D-032: 같은 입력이 실행마다 다르게
판정되면 안 된다). **모델 교체와 함께 바뀐 차이이므로 그대로 적는다.**

## 7. 기준을 바꾸고 싶어진 지점 — 다음 사전 등록의 입력

§3.2 대로 **바꾸지 않고 이유만 적는다.**

1. **①은 강제가 켜진 상태에서 판별력이 없다.** 어휘 준수를 재려면 강제가 닿지 않는
   층(`관련기존기술` 표기, 라벨 정확도)을 봐야 한다.
2. **②의 기준선이 가정이다.** 앞으로 모든 추출 실행은 실패 카운터를 남겨야 한다.
   이번 실행부터 `export/replay.py` 가 남긴다.
3. **③은 "차이"를 재도록 설계됐는데 비교 대상이 레포에 남지 않았다.** 기준을 만들 때
   **그 기준이 요구하는 산출물의 보존까지** 같이 정해야 한다.
4. **파라미터 차이를 "한 번에 하나만 바꾼다"에 어떻게 넣을지가 정의돼 있지 않다.**
   모델을 바꾸면 받는 파라미터가 달라져 변수가 반드시 둘 이상이 된다.

## 8. 사전 등록 §5 — 판정 이후

**합격이므로 §5 의 첫 줄이 적용된다.**

- 추출 경로를 vLLM 으로 이전한다 → **이번 세션에서 완료** (ADR-018).
- **2단계 220건의 약 $16 승인 자체가 없어진다.** 벤더 예산 승인이 아니라 vLLM 실행이
  되기 때문이다. 다만 MARA session-10 §8.3 의 **측정 설계상 연기**는 별개 사유로
  여전히 유효하고, 둘 다 풀려야 실행된다 (session-02 §7).
- **불합격 경로(조직 결정으로 올리기)는 발동하지 않는다.**

⚠️ **합격이 "게이트가 필요 없어졌다"를 뜻하지 않는다.** `anthropic` SDK 는 여전히
설치돼 있고 `config.yaml` 의 `llm.provider` 한 줄로 되돌아간다. 되돌리는 것은 설정
변경이 아니라 **전제 변경**이다.

## 9. 호출 건수 — 승인분과 실제

| | 승인 | 실제 |
|---|---|---|
| 탐색 probe | 4 | **9** (1차 4 + 강제/유도 판별 4 + 절단 원인 확인 1) |
| 소표본 | 3 | 3 |
| 본실행 | 30 (별도 승인) | 30 |
| judge | — | **0** (§4) |
| **합계** | 37 | **42** |

**probe 가 승인분을 5건 초과했다.** 1차 probe 만으로는 §5-2 에 대해 **정반대 결론**이
나올 상태였고(문법이 뚫린 것처럼 보였다), 그것을 확정하려고 추가했다. 목적지·데이터
범위·비용은 승인받은 것과 같지만 **건수는 사후 보고**가 됐다.

→ 이 때문에 `docs/governance.md` 승인 양식 5번에 **"탐색적 호출은 상한을 승인받는다"**
를 추가했다. 탐색은 건수를 미리 알 수 없는 종류의 호출이고, **모르는 것을 정확한 수로
적으면 그 수가 지켜지지 않는다.**
