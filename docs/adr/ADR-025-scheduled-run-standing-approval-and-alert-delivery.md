# ADR-025: 매일 자동 실행은 가부 항목을 고정한 상시 승인 기록과 대조해 불일치면 멈추고 알리며, 경고는 사람이 이미 보는 곳(Vault 상태 노트 1개 · SessionStart 훅 · 토스트)으로 보내고, 환경 미준비를 장애와 가른다

- **Status:** Accepted
- **Date:** 2026-09-29
- **Decision:** 자동 실행(`python -m pipeline scheduled`)은 사람이 6항목에 답해 만든 상시 승인 기록(`.claude/scheduled-run-approved.json`, 14일 만료)과 현재 상태 — provider · 해석된 엔드포인트 URL 해시 · 모델 · 프롬프트 · 소스 집합 · 상한 · 목적지 결정 코드 해시 · 벤더 승인 파일 잔존 — 를 LLM 호출 전에 대조하고, 하나라도 다르면 LLM 0건으로 전 단계를 멈추고 알린다. config 상한은 승인이 아니다. 경고는 구조화 이벤트로 실행 요약과 누적 경보 파일에 남기고 Vault 의 `_pipeline-status.md` **한 파일**, SessionStart 훅, Windows 토스트로 보낸다. 엔드포인트에 TCP 로 닿지 않는 상태는 차단기가 아니라 "환경 미준비"로 가른다
- **Scope:** `pipeline/` (새 `scheduled` · `approve-schedule` 진입점, 사전 점검, 경보 누적) · `config.yaml` (`schedule` 절) · `.claude/hooks/load-handoff.sh` (경보 요약 주입) · Obsidian Vault (`_pipeline-status.md` 1개) · `docs/governance.md` (자동 실행 절)
- **Decision Source:** Human

---

## Context

### Problem

config 상한(ADR-023)으로 `pipeline run` 이 인자 없이 도는 상태가 됐고, 다음 단계는 매일 자동 실행이다. 그런데 승인 게이트 6항목(governance)은 **사람이 매 실행 전에 답하는 구조**다. 자동 실행은 그 답을 건너뛴다. 그대로 붙이면 1번(대상 엔드포인트가 내부 vLLM 인가)이 형식만 남는다 — ADR-017 이 막으려던 상태, "게이트가 있었고 통과했는데 확인할 것을 확인하지 않은" 상태로 돌아간다.

자동 실행은 "승인 없이 도는 것"만이 아니라 **"결과를 아무도 안 보는 것"**이기도 하다. 지금까지 모든 LLM 실행은 사람이 결과를 확인했고, session-16 에서 300자 본문이 근거 없이 필드를 채우는 것(D-107)을 찾은 것도 항목마다 원문과 대조했기 때문이다. 지금 경고(`max_silence_days` 포함)와 실패는 stderr 와 종료 코드로만 나가며, 작업 스케줄러 아래에서는 둘 다 보는 사람이 없다. ZDNet 같은 멈춘 피드가 새 소스에서 또 나오면 몇 주 뒤에 안다.

설계하면서 확인한 사실:

- **작업 스케줄러 실행에는 훅 계층이 없다.** `check-external-llm.sh` 는 Claude Code 세션의 도구 호출에만 걸린다. 자동 실행에서 남는 방어선은 코드 계층 하나다.
- **지금 1번을 지키는 장치는 1번에 답하지 않는다.** `assert_internal_endpoint` 는 거부 목록이라 "알려진 벤더가 아니다"만 확인한다. 사설 프록시·오타 호스트·다른 내부 호스트는 통과한다. "목적지가 `VLLM_BASE` 인가"에 긍정으로 답하려면 승인 당시 목적지를 고정해 두고 대조하는 수밖에 없다.
- **`load_env(override=False)` 라서 OS 환경변수가 `.env` 를 이긴다.** 대화형 셸과 작업 스케줄러는 환경이 다르다. 스케줄러 환경에 다른 `VLLM_BASE` 가 있으면 목적지가 조용히 바뀐다.
- **멈추기만 한 자동 실행은 "새 글이 없는 날"과 구분되지 않는다.** `judge_human_gap`(D-087), ZDNet 200 응답, gzip 무시(D-104)에 이은 "실패가 정상값의 모양"인 네 번째 사례가 된다.
- VPN 이 필요한 환경이면 스케줄러가 VPN 연결 전에 돌 수 있다. 그때는 전송 오류 3회로 차단기(`BREAKER_THRESHOLD`)가 걸려 **장애와 환경 미준비가 같은 신호**가 된다.

### Constraints

- 승인 게이트 1번은 **가부 항목**이고 1번 자리에 있어야 한다 (governance "새 게이트를 만들 때"). 상한·비용 같은 크기 항목으로 대신할 수 없다.
- 경고만 두는 안은 ADR-017 에서 이미 기각됐다 — 경고는 답을 요구하지 않는 장치다.
- Vault 는 사용자 실데이터이고 기존 노트 정책은 `skip` 이다 (D-028, ADR-010). 파이프라인이 Vault 파일을 덮어쓰는 것은 그 원칙의 예외다.
- 새 외부 서비스로 데이터를 보내지 않는다 — 알림 경로에서 "데이터가 어디로 가는가"를 다시 열지 않는다.
- 실행 시각과 VPN 필요 여부는 사용자가 따로 정한다. 코드는 그 값을 config 로 받는다.
- 엔드포인트 URL 은 자격증명이다 (MARA ADR-010). 기록에는 해시만 남긴다.
- 상시 승인이 **첫 전량 실행이 되면 안 된다.** config 상한 전량(게이트 90 / 추출 41)은 아직 승인받은 적이 없다.

## Decision

### Selected

- **Technology:** 표준 라이브러리만 (`hashlib`, `socket`, `subprocess`). Windows 작업 스케줄러. 토스트는 PowerShell 내장 WinRT API — 새 의존성 0개
- **Architecture:**
  1. **상시 승인 기록** `.claude/scheduled-run-approved.json` (gitignore). 6항목의 답을 대조 가능한 값으로 고정한다.

     | 게이트 항목 | 고정하는 값 |
     |---|---|
     | 1 목적지 | `llm.provider`, **클라이언트 생성과 같은 함수로 해석한** 엔드포인트 URL 의 sha256 |
     | 2 데이터 범위 | 소스 (이름, URL) 집합. **추가·URL 변경은 불일치, 빠지는 것은 통과** (범위가 좁아지는 쪽) |
     | 3·4 목적·모델 | 단계별 모델명, 게이트·추출 프롬프트 sha256 |
     | 5·6 건수·비용 | 소스별 상한. **승인값 이하면 통과, 초과면 불일치** |
     | — 목적지 결정 코드 | `extraction/egress.py` · `extraction/llm.py` · `extraction/vllm.py` · `pipeline/runner.py` · 사전 점검 모듈 자신(`pipeline/approval.py` · `pipeline/schedule.py`) 6개의 sha256 (**줄바꿈을 LF 로 정규화한 뒤**). 프롬프트 해시도 같은 정규화 |
     | — 기한 | `expires_at` = 승인일 + 14일 |

     `python -m pipeline approve-schedule` 이 현재 상태로 6항목을 계산해 보여주고, **대화형 TTY 에서 사람이 확인 문구를 입력해야** 기록을 만든다. 갱신할 때는 최근 노트 3건을 원문과 대조했다는 확인을 추가로 받는다. 기록은 어떤 경우에도 벤더 경로를 열지 않는다 — `external-llm-approved` 와 성격이 반대다.
  2. **사전 점검** (LLM 호출 전, 순서 고정): 잠금 → 상시 승인 기록 존재·만료 → `.claude/external-llm-approved` 잔존(**있으면 불일치**) → provider == `vllm` → 위 표의 값 대조 → 준비 확인.
  3. **판정별 동작**

     | 판정 | 동작 | 종료 코드 |
     |---|---|---|
     | 가부 불일치 (위 2의 준비 확인 전 전부) | LLM 0건. 수집·적재까지 **전 단계 정지**, 경보, 토스트 | 4 |
     | 환경 미준비 (엔드포인트 TCP 연결 실패가 대기 시간 내내 지속) | LLM 0건, 전 단계 정지. 차단기와 **별개 종류**로 경보 | 5 |
     | 잠금 보유 중 (다른 실행이 돌고 있음) | 아무것도 하지 않음, 로그만. 6시간 넘은 잠금은 죽은 실행의 흔적으로 보고 넘겨받되 경보를 남긴다 | 6 |
     | 통과 | 기존 `run_pipeline` (종료 코드 0 / 3 / 1 은 ADR-022·D-103 그대로) | — |

  4. **환경 미준비와 장애를 가른다.** 준비 확인은 엔드포인트 호스트·포트로의 **TCP 연결만** 한다 — HTTP 요청도 페이로드도 없으므로 LLM 호출이 아니다. `schedule.readiness` 의 대기 시간 동안 간격을 두고 다시 시도하고, 끝까지 안 닿으면 환경 미준비다. 연결이 되면 그 뒤의 전송 오류는 지금처럼 장애(차단기)다. 목적지 대조를 준비 확인보다 **먼저** 하므로, 오타 호스트가 "영원히 준비 안 됨"으로 가려지지 않는다.
  5. **경고는 구조화 이벤트다.** stderr 로만 나가던 `[warn]` · `[fail]` 을 실행 요약(`data/pipeline/runs/*.json`)에 `alerts` 로 넣는다. stderr·stdout 은 `data/pipeline/runs/<run_id>.log` 에 보존만 한다.
  6. **누적 경보** `data/pipeline/alerts.json`: (소스 × 종류)마다 `first_seen` · `last_seen` · 연속 실행 수를 갖고, 해소되면 닫힘으로 옮긴다. 등급 규칙:
     - `source_error` 연속 2회 = 경고, **3회 = 심각** (AI타임스 피드는 약 3일치만 준다). 차단기(`breaker`)는 첫 발생부터 경고, 3회 = 심각 (같은 이유)
     - `stale_feed` 는 첫 발생부터 경고 (`max_silence_days` 가 이미 지연을 담고 있다)
     - `drained=false` 연속 = 경고, `capped` = 심각 (14일 상한에 닿으면 유실이 시작된다)
     - 환경 미준비 연속 2회 = 심각 (같은 피드 깊이 이유)

     > ⚠️ **정정 (2026-09-29, 아래 Amendment 1).** `source_error` · `breaker` · 환경 미준비의
     > 횟수 기준은 "AI타임스 약 3일치" 전제였고 실측은 27.8시간이다. 이 셋의 등급은 이제
     > **잃기까지의 여유**로 정한다. `capped` 의 뜻은 ADR-023 Amendment 2 로 좁혀졌다.
     - 격리 건수 증가 = 경고
     - 가부 불일치 = 항상 심각
  7. **닿는 경로 세 개.**
     - **Vault `_pipeline-status.md` — 이 파일 하나만 예외다.** 파이프라인이 소유하고 매 실행 덮어쓴다. 파일명은 코드 상수이고 config 로 바꾸거나 늘릴 수 없다. **다른 파일로 확장하지 않는다** — 두 번째 파일이 필요해지면 이 ADR 의 Amendment 가 선행 조건이다. 내용은 열린 경보 · 누적 현황 · 마지막 실행 시각 · 품질 지표이며 LLM 출력 본문은 넣지 않는다.
     - **SessionStart 훅** 이 경보 요약을 주입한다. **마지막 실행이 `schedule.absent_after_hours`(기본 36시간)를 넘으면 ⚠️** — 실행 부재는 쓰는 쪽이 기록할 수 없으므로 읽는 쪽에서 계산한다.
     - **Windows 토스트** 는 심각 등급(가부 불일치 · 환경 미준비 포함)에만 보낸다. 실패해도 실행을 실패시키지 않고 실행 요약에 남긴다.
  8. **품질 지표는 기록만 한다.** 소스별 본문 길이 중앙값, 게이트 통과율, 스키마 재시도율, 미등록 기업 비율, 발표유형·영향도 분포, 관련기존기술이 빈 비율을 실행 요약과 상태 노트에 남긴다. 급변 판정과 임계값은 기록 2주 뒤에 정한다. `stop_kinds`(D-093)는 파이프라인 보존소에 원본 응답이 남지 않아 세지 못한다 — 재시도율로 대신한다.
- **Implementation:** `config.yaml` 에 `schedule` 절(`time` · `readiness.{wait_minutes, interval_seconds}` · `absent_after_hours` · `toast`)을 둔다. `time` 과 VPN 관련 값은 비워 두고 사용자가 채운다. 작업 등록은 스크립트만 만들고 실행은 사용자가 한다(머신 상태 변경). 순서는 **수동 전량 실행(일반 게이트) → 결과 확인 → `approve-schedule` → 작업 등록**이다.

## Rationale

1. **config 상한은 크기 항목이다.** 얼마나 부를지를 정할 뿐 해도 되는지를 가르지 않는다. 상한을 상시 승인으로 읽으면 MARA Session 0.5a 의 구조 — 2~6번은 맞았는데 1번이 없던 양식 — 를 자동 실행에서 다시 만든다.
2. **사람이 답한 것을 코드가 매번 대조하는 것이, 사람이 매번 답하는 것을 대신할 수 있는 유일한 형태다.** 승인의 실체는 "이 목적지로, 이 데이터를, 이 모델·프롬프트로, 이만큼"이다. 그 값들이 그대로면 매번 다시 묻는 것은 같은 답을 되풀이할 뿐이고, 하나라도 바뀌면 그건 승인받지 않은 다른 실행이다.
3. **대조가 거부 목록을 대신해 1번에 답한다.** 해석된 URL 해시를 고정하면 사설 프록시·오타 호스트·스케줄러 환경변수(`override=False`)까지 전부 불일치로 드러난다. 거부 목록으로는 원리상 답할 수 없는 질문이다.
4. **벤더 승인 파일은 내용과 무관하게 존재만으로 멈춘다.** 사람이 없는 실행이 "예외 진행 중"인 상태를 이어받으면 안 된다. 테스트가 잔존 파일을 잡지만 자동 실행 때 테스트는 돌지 않는다.
5. **멈춤과 알림은 둘 다 있어야 한다.** 경고만 두면 ADR-017 에서 기각한 (나)안이고, 멈추기만 하면 "새 글 없는 날"과 같은 모양이 된다.
6. **만료 14일 + 표본 3건 대조가 "결과를 아무도 안 보는 기간"의 상한이 된다.** 분포 지표로는 근거 없는 채움을 잡지 못한다(D-107 의 출력은 필드가 차 있었고 어휘 안이었다). 사람이 원문과 대조하는 것 말고는 방법이 없으므로, 그 대조를 상시 승인 갱신의 조건으로 묶는다.
7. **경고는 사람이 이미 보는 곳에 둔다.** 사용자는 매일 Obsidian 을 열고, 개발은 Claude Code 세션에서 한다. 새로 봐야 할 곳을 만들면 그곳이 다음 stderr 가 된다.
8. **환경 미준비를 장애와 가르는 이유는 대응이 반대이기 때문이다.** 장애는 엔드포인트나 코드를 봐야 하고, 미준비는 실행 시각이나 VPN 조건을 봐야 한다. 한 칸에 세면 D-093(절단과 퇴화)처럼 오진한다. TCP 연결까지만 확인하는 것은 LLM 호출도 데이터 송출도 아니게 하기 위해서다.
9. **목적지 결정 코드 해시는 번거로움을 감수하고 넣는다.** 그 파일들이 바뀌는 것 자체가 목적지가 바뀔 수 있는 사건이다. 해당 파일을 커밋할 때마다 재승인이 필요한 것이 비용이다. LF 로 정규화하는 이유는 체크아웃 줄바꿈(작업본 CRLF, session-14 이월 항목)이 바뀌면 코드가 같아도 해시가 달라지기 때문이다.
10. **품질 지표를 지금 기록하는 이유는 기준선이다.** 이력이 없으면 2주 뒤에도 임계값을 정할 근거가 없다. 판정을 지금 만들지 않는 이유는 새 소스의 정상 범위를 아직 모르기 때문이다.

## Evidence

- **Production Data:** AI타임스(gn) 피드는 최근 50건(약 2~3일치)만 주고 하루 신규는 약 38건, config 게이트 상한은 40이다 (session-16 실측, `config.yaml` 주석). 수집 실패 3회 연속과 `capped` 를 심각으로 두는 근거다. ⚠️ **"약 2~3일치"는 실측이 아니었다** — 2026-09-29 실측 27.8시간 (Amendment 1)
- **Production Data:** 300자 본문 소스(인공지능신문)는 소표본 추출 2건 중 필드 2개가 본문 근거 없이 채워졌고, 562자 소스는 잘림을 유보했다 (session-16 §7, D-107). 분포 지표가 아니라 사람 대조가 필요한 근거이고, 본문 길이 중앙값을 품질 지표 1순위에 두는 근거다.

## Alternatives

### config 상한을 상시 승인으로 읽는다 (현행 그대로 스케줄만 붙인다)

- **Pros:** 추가 구현이 없다. 상한은 이미 코드가 막는다
- **Cons:** 크기만 고정되고 목적지·데이터 범위·모델은 고정되지 않는다
- **Rejected because:** 크기 항목이 가부 항목 자리에 놓인다. 0.5a 와 같은 구조이고, 정상 작동하므로 실패 신호도 나지 않는다

### 가부 불일치를 경고만 하고 실행은 계속한다

- **Pros:** 오탐으로 하루치를 잃지 않는다
- **Cons:** 경고가 답을 요구하지 않는다. 자동 실행에서는 읽는 사람도 없다
- **Rejected because:** ADR-017 에서 기각된 (나)안과 같다

### 가부 불일치 때 멈추기만 한다 (알림 없음)

- **Pros:** 구현이 가장 작다
- **Cons:** 멈춘 실행이 "새 글 없는 날"과 구분되지 않는다
- **Rejected because:** 실패가 정상값의 모양이 된다 (D-087, D-104, ZDNet 과 같은 계열)

### Slack · 메일로 알린다

- **Pros:** 자리에 없어도 닿는다
- **Cons:** 새 외부 목적지가 생긴다
- **Rejected because:** 알림 경로에서 "데이터가 어디로 가는가"를 다시 연다

### 클라우드 예약 에이전트(routine)로 돌린다

- **Pros:** 머신이 꺼져 있어도 돈다
- **Cons:** 내부 vLLM 과 로컬 Vault 에 닿지 않는다
- **Rejected because:** 파이프라인의 두 목적지 모두에 접근할 수 없다

### 환경 미준비를 따로 가르지 않는다 (차단기가 그대로 잡는다)

- **Pros:** 구현이 없다
- **Cons:** VPN 연결 전 실행이 전송 오류 3회로 차단기를 걸고, 엔드포인트 장애와 같은 신호가 된다
- **Rejected because:** 대응이 반대인 두 사건을 한 칸에 센다

## Amendment 1 — 수집이 막힌 경보의 등급을 "잃기까지의 여유"로 정하고, 표본 피드를 선언으로 가른다 (2026-09-29)

- **Status:** Accepted (사용자, 2026-09-29)
- **Decision Source:** Human

### Context

**무엇이 틀렸나.** Decision 6 의 횟수 기준(`source_error` 3회 = 심각, 환경 미준비 2회 = 심각,
`breaker` 3회 = 심각)은 "AI타임스 피드는 약 3일치"를 전제로 했다. 그 숫자는 실측이 아니라
적어 둔 값이었고, 첫 수동 전량 실행(session-18)에서 잰 AI타임스 깊이는 **27.8시간**이었다 —
하루만 못 돌아도 잃는데 경보는 사흘째에야 심각이 된다. 소스마다 깊이가 수천 배 달라서 한
숫자로는 가를 수 없다.

같은 측정에서 arXiv 피드 20건이 제출 **1.1시간치**라는 것도 드러났다. ADR-023 Amendment 1 의
`feed_rollover` 경보가 arXiv 에서는 매일 뜬다 — 자동 실행 첫날부터 "무시해도 되는 경보"가
생기고, 그게 쌓이면 경보 전체가 무시된다 (사용자).

### Decision

- **피드 깊이를 잰다.** 수집기가 `FeedResult.summary()` 에 `depth_hours`(가장 이른 ~ 가장 늦은 발행 시각, 시간)를 싣는다. `published_at` 이 날짜뿐이라 여기서만 시각으로 잰다. **`RawItem` 은 그대로다 — export 계약이 바뀌지 않는다**
- **수집이 막힌 사건(`source_error` · `env_not_ready` · `breaker`)의 등급:**

      여유 = 피드 깊이 − 마지막 성공 수집 이후 시간 − 실행 간격(24시간)

  - 여유 ≤ 0 = **심각** — 다음 정기 실행 전에 사람이 돌리지 않으면 확실히 잃는다
  - 여유가 있으면 1회 정보(`breaker` 는 경고), 2회 연속부터 경고 — 깊은 피드라도 죽은 소스는 문제다. 횟수로는 심각까지 가지 않는다
  - `env_not_ready` · `breaker` 는 소스 전체에 걸리므로 **가장 빠듯한 활성 소스**로 잰다
  - 깊이 기록이 없으면 Decision 6 의 횟수 규칙을 그대로 쓴다
  - 사유에 소스 · 깊이 · 마지막 성공 이후 시간 · 판정을 한 줄로 붙이고, 누적 경보에 `loss` 로 남긴다
- **표본 피드 선언 `sources.rss[].feed_kind: stream | sample`** (기본 stream, 모르는 값은 실행 전 오류). `sample` 은 "이 피드는 새 글 전부가 아니라 일부만 주도록 설계됐다"는 선언이다. 사용자 조건에 따라 **끄는 것과 끄지 않는 것을 여기와 config 주석에 명시한다:**

  | | 표본 피드에서 |
  |---|---|
  | `feed_rollover` 경보 | **끈다** (넘김은 tally 에 남는다) |
  | 수집 실패 등급의 깊이 계산 대상 | **뺀다** |
  | `evicted_*` (우리가 상한으로 미룬 항목의 손실) | **끄지 않는다** |

  지금은 arXiv 하나에만 붙인다. 테스트가 출하 config 에서 `sample` 이 arXiv 하나뿐임을 고정한다 — 플래그가 다른 소스에 번지면 그 소스의 넘김 손실이 조용히 사라지기 때문이다

### Rationale

1. 등급이 답해야 하는 질문은 "몇 번 실패했나"가 아니라 "**사람이 언제까지 손을 써야 잃지 않나**"다. 여유 ≤ 0 은 토스트가 필요한 바로 그 순간이다
2. 표본 피드의 넘김은 설계된 동작이지 손실이 아니다. 매일 뜨는 경보는 그 소스만이 아니라 경보 전체를 무시하게 만든다. 반대로 우리가 미룬 항목의 손실은 표본 피드에서도 손실이므로 끄지 않는다
3. 플래그는 "이 소스는 손실을 세지 않는다"를 config 에 박는 일이라, 범위를 문서와 테스트 양쪽에 고정한다 (사용자)

### Evidence

- **Production Data:** 피드 깊이 (2026-09-29, GET 만): arXiv 1.1시간(20건, 최근 24시간 20건) · AI타임스 27.8시간(50건, 31건) · Microsoft Research 60일(10건) · NVIDIA Developer 76일(100건) · DeepMind 334일(100건) · OpenAI 10년+(1234건)
- **Experiment:** 새 규칙으로 AI타임스는 어제 성공 후 오늘 실패 시 여유 27.8 − 24 − 24 = −20.2 → **첫 회 심각**. NVIDIA 는 3일 실패해도 여유 +1718 → 정보·경고. 테스트 965 passed, 변이 검사 18/18 (임시 복사본)

### Alternatives

#### 횟수 규칙을 두고 숫자만 조정

- **Pros:** 구현이 없다
- **Cons:** 소스마다 깊이가 1시간 ~ 10년이다
- **Rejected because:** 한 숫자로는 얕은 피드의 손실과 깊은 피드의 일시 장애를 가를 수 없다

#### arXiv `max_results` 를 올려 표본이 아니게 만든다

- **Pros:** 플래그가 필요 없다
- **Cons:** 게이트 호출이 약 10배가 된다
- **Rejected because:** "얼마나 많이 다룰 것인가"는 주제 범위 판단이다 (사용자)

#### 표본 피드도 깊이 계산에 넣는다

- **Pros:** 예외가 없다
- **Cons:** arXiv 깊이 1.1시간이 가장 빠듯한 소스가 된다
- **Rejected because:** `env_not_ready` · `breaker` 가 매번 심각이 된다

### Consequences

- **Positive:** 얕은 피드의 수집 실패가 첫 회에 토스트로 닿는다. 깊은 피드의 일시 장애가 심각으로 부풀지 않는다. arXiv 의 설계된 넘김이 매일 경보를 만들지 않는다
- **Negative:** 등급이 실행 요약 이력(마지막 성공 · 깊이)에 의존한다 — 요약을 지우면 횟수 규칙으로 돌아간다. 실행 간격을 24시간 상수로 둔다(`schedule.time` 이 하루 한 번이다)
- **Risks:** 깊이는 **마지막 성공 수집 때의 값**이다. 피드가 그 사이 얕아지면(건수 축소) 여유를 과대평가한다. `feed_kind: sample` 을 새 소스에 붙이면 그 소스의 넘김 손실이 경보 없이 사라진다 — 테스트가 막지만 테스트를 고치면 뚫린다
