# ADR-014: judge 루브릭을 버전으로 올리고, 효과를 사전 등록 기준 + 대조군으로 검증한다

- **Status:** Accepted
- **Date:** 2026-08-30
- **Decision:** judge 루브릭을 `summary_quality.v2`(간결성 기준 정정) → `v3`(완결성 축에 핵심 정보 4슬롯 정의)로 올리고, v3 의 효과를 **가설·임계값을 데이터 전에 고정한 상태에서 v2 대조군과 함께** 실측해 확인한다.
- **Scope:** ai-news-ontology (eval / judge)
- **Decision Source:** Human

> 이관: README 결정 로그 **D-041**(v2), **D-045**(v3), **D-048**(검증). 루브릭을 바꾸고
> 그 효과를 확인하기까지가 한 결정이라 묶었다. Date 는 시작 시점(D-041)을 쓰고,
> 검증 실행일(2026-09-01)은 Evidence 에 적는다.

---

## Context

### Problem

`summary_quality.v1` 은 `요약` 필드가 생기기 전(ADR-007)에 쓴 초안이라 **스키마 규칙을
지킨 요약이 오히려 감점되는** 구조였다 — 2~3문장으로 쓰면 간결성 3점.

그 뒤 첫 실행에서 완결성이 judge 3점 / 사람 1점으로 갈렸다. "구간이 뭉뚱그려져 있어서"로
잠정 진단했으나, **누락 목록을 대조해 보니 합집합 6개 중 1개만 겹쳤다.** 둘은 같은
누락을 다르게 채점한 것이 아니라 **서로 다른 것을 세고 있었다** — judge 는 독자
영향(범위·재현성·심각도), 사람은 기술적 detail(발견 비용·신호·수정안).

### Constraints

- 채점기가 채점 대상의 계약을 모르면 자기 기준으로 판단한다.
- 구간 세분화만으로는 부족하다. **셀 대상을 먼저 고정**해야 한다.
- v3 만 반복하면 "v3 가 점수를 옮겼다"와 "judge 가 원래 2~3을 오가는데 우연히 3을
  뽑았다"를 구분할 수 없다.

## Decision

### Selected

- **Technology:** 마크다운 루브릭 파일 + 반복 채점 스크립트
- **Architecture:** 완결성 축에 **핵심 정보 4슬롯**(사건/범위/정도/경위)을 정의하고
  슬롯 충족 개수로 구간을 세분화한다. 충실성·간결성은 v2 그대로 둔다.
  "이름만 언급하면 미충족" 규칙을 함께 넣는다 — 슬롯을 절반만 채운 경우를 충족으로
  세면 구간을 나눈 의미가 사라지기 때문이다.
- **Implementation:** `eval/judge_prompts/summary_quality.v2.md`, `v3.md`.
  v1·v2 는 보존한다 (ADR-004). v2 에서 출력 형식 절을 지운 것은 스키마가 structured
  outputs 로 주입되기 때문이다(ADR-003) — 프롬프트에 또 적으면 미러가 하나 더 생긴다.

## Evidence

- **Experiment:** 2026-09-01, 골든셋 #33001 을 v3 로 10회, **v2 로 5회(대조군)** 반복 채점.
  완결성은 v3 8/8회 **2점**, v2 5/5회 **3점**. 손계산 예상(2점)이 그대로 재현됐다.
  결정적이었던 것은 점수가 아니라 **근거**다 — `slot_fill_rate` 가 8회 모두
  ①1.00 / ②③④0.00 으로 같은 슬롯을 같은 이유로 판정했다.
- **Experiment:** 같은 15회 실측에서 비결정성은 완결성·충실성 변동 0회, 간결성만
  8회 중 2회였다.

## Rationale

1. 채점기가 채점 대상의 계약을 모르면 자기 기준으로 판단한다 — v1 의 간결성 기준이
   스키마와 어긋나 있던 것이 그 사례다.
2. 완결성 격차의 원인은 구간이 아니라 **세는 대상**이었다. 그래서 구간 세분화보다
   슬롯 정의가 먼저다.
3. **대조군을 함께 돌린 것이 이 실행의 핵심이다.** 대조군이 없으면 루브릭 변경 효과와
   judge 의 원래 흔들림을 가를 수 없고, 1건으로 편향을 주장하지 않기로 한 원칙
   (README D-043)을 한 층 위로 옮기는 데 그친다.
4. 판정 기준과 임계값을 **데이터를 보기 전에 고정**했다. 실행 후에 정하면 어떤
   결과든 성공으로 읽힌다.

## Alternatives

### v1 을 직접 수정

- **Pros:** 파일이 늘지 않는다.
- **Cons:** 버저닝 관례의 예외가 된다 (ADR-004).
- **Rejected because:** 관례에 예외를 두면 관례가 아니다.

### 스키마의 문장 수 규칙을 3~5문장으로 되돌림

- **Pros:** 루브릭을 안 고쳐도 된다.
- **Cons:** 요약 필드의 설계 의도(ADR-007)를 채점기 사정에 맞춰 바꾸는 것이다.
- **Rejected because:** 계약을 모르는 쪽을 고치는 게 맞다.

### judge 를 Haiku 로 내려 temperature 고정 / 3회 다수결

- **Pros:** 비결정성을 없앨 수 있다.
- **Cons:** 전자는 채점 품질을 떨어뜨리고 후자는 비용이 N배다.
- **Rejected because:** 15회 실측에서 변동이 가정보다 훨씬 작았다 — 감수할 근거가
  사라졌다. 다만 "judge 는 결정적이다"로 뒤집지도 않는다(항목 1건 기준이고 간결성은
  실제로 갈렸다).

## Consequences

### Positive

- 루브릭 변경의 효과를 주장이 아니라 실측으로 말할 수 있게 됐다.
- 슬롯 판정을 읽는 집계기를 순수 함수로 분리해(README D-051) 저장된 결과를
  **API 재호출 없이** 재집계할 수 있다.

### Negative

- 루브릭 버전이 바뀌면 과거 점수와 단절된다. 문구 하나를 고치는 데도 v4 가 필요하고,
  그러면 v3 의 검증이 v4 에 대해서는 다시 미검증이 된다 (README D-055).
- 슬롯 판정이 이분법이라 "부분 충족"을 표현할 칸이 없다는 결함이 남았다 (README D-060).

## Reversibility

- **Reversible:** Partial
- **Rollback:** 이전 버전 파일이 보존돼 있어 되돌릴 수 있지만, 점수 추이가 끊긴다.
- **Migration Cost:** Medium
