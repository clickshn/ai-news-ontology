# ADR-008: 어휘는 값 추가만 스키마에서 하고, 판단 기준 변경은 문서·프롬프트에서 한다

- **Status:** Accepted
- **Date:** 2026-08-29
- **Decision:** 통제어휘에 **값을 추가**하는 것은 스키마(Enum)에서 하고, 기존 값의 **판단 기준을 좁히는** 것은 스키마를 건드리지 않고 문서·프롬프트 층위에서만 한다.
- **Scope:** ai-news-ontology (온톨로지 어휘)
- **Decision Source:** Human

> 이관: README 결정 로그 **D-021**(`Community/Discussion` 추가), **D-022**(`Agent` 를
> 쪼개지 않음). 두 항목이 각각 "값 추가"와 "기준 변경"의 사례이고 하나의 정책을
> 이루므로 묶었다. 원본 날짜와 근거는 그대로다.

---

## Context

### Problem

첫 추출에서 두 가지 문제가 같이 드러났다.

1. 커뮤니티 발 버그 발견 글이 갈 곳이 없어 `Benchmark/Report` 로 밀려났다.
2. LLM 보조로 작성한 퍼저가 `기술영역: Agent` 로 분류됐다 — 기준이 너무 넓다.

둘 다 "어휘를 손봐야 한다"로 보이지만 필요한 조치가 정반대였다.

### Constraints

- **어휘를 쪼개거나 이름을 바꾸면 이미 쌓인 노트의 라벨이 소급해서 틀린 것이 된다.**
  재인덱싱·재라벨링 없이는 복구되지 않는다.
- 값을 **추가**하는 것은 과거 라벨을 무효화하지 않는다.
- 판단 기준은 사례가 쌓이며 계속 바뀌는 종류다.

## Decision

### Selected

- **Technology:** `StrEnum` (값 추가) / 마크다운 문서와 프롬프트 (기준 서술)
- **Architecture:** 변화의 **방향**에 따라 층위를 다르게 둔다. 값 추가는 스키마,
  기준 변경은 문서·프롬프트.
- **Implementation:** `발표유형` 에 `Community/Discussion` 추가(6개 → 7개).
  가르는 기준은 "무엇을"이 아니라 **"누가"** — 공식 조직이면 다른 값, 개인·커뮤니티면
  이 값. `기술영역: Agent` 는 Enum 을 그대로 두고 `schema.md` 와 프롬프트에서만 좁힌다.

## Rationale

1. 값 추가는 과거 라벨이 여전히 유효하지만, 값을 쪼개면 **이미 쌓인 노트가 소급해서
   틀린 것이 된다.** 두 변화는 비용이 다르므로 같은 방법으로 다루면 안 된다.
2. 판단 기준은 사례가 쌓이며 계속 바뀌므로 문서가 맞는 층위다. 기준이 바뀔 때마다
   스키마를 고치면 어휘가 흔들린다.
3. `Incident/BugReport` 도 후보였으나 관측된 빈 칸은 "버그"보다 **"커뮤니티 발 글"** 이
   더 정확한 설명이었다.

## Alternatives

### `Incident/BugReport` 를 추가

- **Pros:** 관측된 사례(버그 발견 글)를 직접 가리킨다.
- **Cons:** 빈 칸의 실제 모양과 어긋난다 — 커뮤니티 글에는 버그 아닌 것도 많다.
- **Rejected because:** 값의 이름이 관측을 정확히 설명하지 못한다.

### 어휘를 유지하고 오분류를 감수

- **Pros:** 어휘가 안정적으로 유지된다.
- **Cons:** GeekNews 를 유지하는 이상 이 부류가 계속 들어온다 (ADR-006).
- **Rejected because:** 반복되는 오분류는 어휘 결함이다.

### `기술영역: Agent` 를 세분화

- **Pros:** 기준이 스키마에 박혀 모호함이 없다.
- **Cons:** 과거 노트의 `Agent` 라벨이 소급해서 틀린 것이 된다.
- **Rejected because:** 되돌릴 수 없는 비용을 기준 조정에 지불하게 된다.

## Consequences

### Positive

- 어휘 변경 요구가 들어올 때 "이건 추가인가 기준 변경인가"를 먼저 묻게 된다.
- 출력 계약이 이 정책을 그대로 받아 갔다 — MARA 는 값 추가를 통과시키고 삭제·개명·
  쪼개짐은 import 실패로 다룬다 (MARA ADR-018, 계약 §5).

### Negative

- 기준이 문서에만 있으면 자동 검증 대상이 아니다. 모호함이 남아 나중에 다시 좁혀야
  했다 (ADR-016 의 "누가" 규칙 명확화).

### Risks

- 값 추가만 허용해도 어휘가 단조 증가한다. 언젠가 정리가 필요해지면 그때가 곧
  소급 비용을 내는 시점이다.

## Reversibility

- **Reversible:** No
- **Rollback:** 추가한 값을 되돌리면 그 값으로 라벨링된 노트가 갈 곳을 잃는다.
  기준 변경은 문서만 고치면 되므로 되돌릴 수 있다 — **정책의 두 갈래가 되돌리기
  비용에서 갈린다는 것이 이 결정의 핵심이다.**
- **Migration Cost:** High (값 변경) / Low (기준 변경)
