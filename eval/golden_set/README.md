# eval/golden_set/

사람이 직접 라벨링한 정답 세트. **커밋 대상**이며 이 프로젝트에서 가장 오래 남는 자산.

## 형식
한 건 = 파일 하나(`{yyyymmdd}-{slug}.json`) 또는 `golden.jsonl` 한 줄.
파일 단위를 기본으로 한다 — diff 리뷰가 쉽고 충돌이 적다.

```json
{
  "id": "20260829-anthropic-claude-opus-5",
  "source_url": "https://example.com/post",
  "input": { "title": "...", "body": "..." },
  "expected": {
    "기술영역": ["LLM", "Reasoning"],
    "발표유형": "ProductLaunch",
    "관련기업": ["Anthropic"],
    "관련기존기술": ["Transformer"],
    "영향도": { "점수": 4, "근거": "..." }
  },
  "reference_summary": "사람이 쓴 3~5문장 요약 (judge 의 참조용, 정답 아님)",
  "human_summary_scores": { "충실성": 5, "완결성": 4, "간결성": 4 },
  "labeled_by": "clickshn",
  "labeled_at": "2026-08-29",
  "notes": "판단이 갈렸던 지점 기록"
}
```

## 골든셋 후보 (검토 대기)

> **모델 출력은 정답이 아니다.** 아래는 파이프라인 실행 결과일 뿐이며,
> 사람이 검토해 라벨을 확정한 뒤에만 골든셋 파일로 승격한다. 모델 출력을
> 그대로 정답으로 삼으면 eval 이 "모델이 스스로를 채점하는" 구조가 된다.

| 날짜 | 항목 | 실행 | 상태 |
|---|---|---|---|
| 2026-08-29 | GeekNews `바이브코딩으로 만든 퍼저가 FFmpeg의 0 나누기 버그를 발견` ([#33001](https://news.hada.io/topic?id=33001)) | gate(Haiku) → extract **v1 → v2 재추출 완료** | **확정 후보** (아래 판단 참고) |
| 2026-08-29 | GeekNews `SpaceX의 Cursor 인수 이후 OpenAI가 내린 결정` ([#33003](https://news.hada.io/topic?id=33003)) | gate(Haiku) → extract v2 → **v4 재추출** | **확정 완료** (2026-09-01) |
| 2026-08-31 | arXiv `S3Gym: Can LLMs Turn Self-Testing and Self-Judging into Self-Improvement?` ([2608.31100](https://arxiv.org/abs/2608.31100v1)) | gate(Haiku) → extract v3 | **확정 완료** (2026-09-01) |

확정 절차: 위 항목을 사람이 라벨링 → 아래 형식의 JSON 파일로 저장 →
`notes` 에 모델 출력과 다른 부분과 그 이유를 남긴다.

### #33001 (FFmpeg) — v1 → v2 재추출 결과

D-020·D-021·D-022 세 규칙이 **모두 라벨을 바꿨다.**

| 필드 | v1 | v2 |
|---|---|---|
| 기술영역 | `Application/Product`, `Agent` | `Application/Product` |
| 발표유형 | `Benchmark/Report` | `Community/Discussion` |
| 관련기존기술 | `퍼징(Fuzzing)`, `바이브코딩` | `Fuzzing`, `Vibe Coding` |
| 영향도 | 2 | 2 (근거 표현만 다름) |

**판단: 정답으로 확정할 만하다.** 네 필드 모두 문서화된 기준에 부합한다.
다만 확정 전에 사람이 확인할 것 —
- `영향도 2` 가 적정한가. v1/v2 가 모두 2를 냈지만 두 판정 모두 같은 모델이라
  일치가 근거가 되지 못한다. **사람 점수를 따로 매겨 `human_summary_scores` 에 남길 것.**
- `관련기업` 에 `FFmpeg`(오픈소스 프로젝트)이 들어간 채로 둘지 → 아래 "관찰 필요" 참고.

### #33003 (OpenAI/Cursor) — 보류 사유 (2026-09-01 재확인)

**2026-09-01 해결.** `Partnership/Contract` 를 추가하고(D-056) v4 로 재추출해
확정했다. `발표유형` 이 `Funding/M&A` → **`Partnership/Contract`**, SpaceX 역할이
`경쟁사` → **`인수 주체`** 로 바뀌었고, GeekNews 소스인데도 `Community/Discussion`
으로 밀리지 않았다(D-057 검증). 사람은 모델 초안에서 세 필드를 고쳤다 — `기술영역`
2개→1개, `관련기업` 4개→3개(xAI 제외), `관련기존기술` 1개→0개.

아래는 보류 당시의 기록이며, 판단의 경로를 남기기 위해 지우지 않는다.

## 라벨링 규칙
- **애매했던 건을 우선 넣는다.** 쉬운 건 100개보다 경계 사례 20개가 낫다.
- `기술영역`이 3개를 넘으면 그건 기사가 아니라 주간 요약이다 — 골든셋에서 제외.
- `notes` 에 "왜 이 라벨인지"를 남긴다. 나중의 나와 judge 루브릭이 이걸 참고한다.
- 목표 규모: 1차 30건, 2차 100건.

### 영향도 점수는 루브릭 밖 기준을 섞지 않는다 (D-046)

**`영향도` 는 원문 내용과 기술적 파급력만 근거로 매긴다.** 아래 기준을 점수에
반영하지 않는다.

| 섞지 말 것 | 왜 |
|---|---|
| AI 엔지니어링 **직무 관련성** | 그건 이미 **관련성 게이트**가 판정한 축이다(`schema.md` "수집 대상 범위"). 게이트를 통과해 여기까지 온 기사에 같은 기준을 두 번 적용하면 한 축을 두 번 세는 셈이고, eval 은 게이트 성능과 영향도 정확도를 구분하지 못하게 된다 |
| 개인적 관심사 | 재현되지 않는다. 다른 사람이(또는 6개월 뒤의 내가) 같은 기사에 같은 점수를 매길 수 없으면 정답으로 쓸 수 없다 |
| 포트폴리오 목적 | 채점 대상이 아니다. 라벨은 모델을 재는 자이지 프로젝트를 홍보하는 자리가 아니다 |

판단 기준은 `schema.md` 의 1~5 척도(국소적 → 도메인 종사자 → 업계 일반 → 판도
변화 → 패러다임 전환) **하나뿐**이다. 근거에는 "원문의 어떤 사실이 척도의 어느
칸에 해당하는가"만 쓴다.

> 이 규칙이 왜 생겼는지는 아래 "라벨링 규칙 이전 항목" 참고. 규칙은 사후에 생긴
> 것이므로, 그 이전 라벨을 소급해서 고치지 않는다.

### 라벨링 규칙 이전 항목

`labeling_guideline` 필드에 어떤 규칙 아래에서 매긴 라벨인지 적는다. 프롬프트
버전을 기록하는 것과 같은 이유다(D-010) — 규칙이 바뀌면 라벨의 의미도 바뀌는데,
어느 규칙에서 나온 라벨인지 모르면 나중에 재라벨링 대상을 고를 수 없다.
