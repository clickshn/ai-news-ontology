# eval/

요약·구조화 품질 검증. **"LLM이 그럴듯하게 썼다"와 "맞게 썼다"를 구분하는 레이어.**

## 두 가지 채점 축

| 축 | 대상 | 방법 | 지표 |
|---|---|---|---|
| 골든셋 대조 | `기술영역`, `발표유형`, `영향도` | 정답과 직접 비교 (결정적) | accuracy, macro-F1, 영향도 QWK |
| LLM-judge | `요약` | 루브릭 기반 1~5 채점 | 충실성 / 완결성 / 간결성 평균 |

요약은 정답 문자열이 하나가 아니라서 exact match 가 무의미하다. 반대로 통제어휘
필드는 judge 를 쓸 이유가 없다 — 그래서 축을 나눴다. (결정 로그 D-006)

## 디렉터리
- `golden_set/` — 사람이 라벨링한 정답. **커밋한다.** 이 프로젝트의 자산.
- `judge_prompts/` — judge 루브릭. 프롬프트도 코드처럼 버전 관리한다.
- `scores/` — 실행 결과 JSON. **gitignore.** 재현 가능한 산출물이므로.

## 실행

```bash
# 대조만 — API 호출 없음. 채점 로직을 고칠 때는 항상 이쪽으로 돌린다.
python -m eval.runner --predictions eval/scores/preds.jsonl --no-judge

# judge 포함 — 실제 API 호출. CLAUDE.md 규칙에 따라 사전 확인이 필요하다.
python -m eval.runner --predictions eval/scores/preds.jsonl --judge

# 같은 항목을 N회 반복 채점 — judge 흔들림 폭을 잰다. **비용이 N배다.**
# --judge-prompt 로 루브릭을 바꿔 두 번 돌리면 루브릭 간 비교가 된다.
python -m eval.runner --predictions preds.jsonl --judge     --judge-prompt summary_quality.v3.md --repeat 10
```

`--predictions` 는 `{"item_id": ..., "ontology": {...}}` JSONL 이다. 채점할 때마다
추출을 다시 돌리지 않는 이유는 비용이다 — 채점 로직을 고치는 동안 API 를 부르면
CLAUDE.md 의 호출 규칙이 무의미해진다.

## 이 단계의 설계 판단

### 초안과 정답을 스키마로 갈라 놓았다 (D-039)
골든셋 항목에 `status: draft | confirmed` 를 두고, 로더가 기본적으로 `confirmed`
만 읽는다. "모델 출력은 정답이 아니다"는 원칙(`golden_set/README.md`)을 주석이
아니라 **코드로** 강제한 것이다. 초안이 실수로 섞이면 eval 이 모델의 자기 채점이
되는데, 그때 점수는 높게 나오고 그 사실이 드러나지 않는다.

`confirmed` 로 올리는 순간 `영향도`·`본문`·`labeled_by`·`labeled_at` 이 모두
있어야 하고, `<<채워주세요>>` 자리가 남아 있으면 검증에서 걸린다. 채점기가
"정답이 없음"과 "정답이 X"를 구분하지 못하면 accuracy 가 의미를 잃기 때문이다.

### 필드마다 채점 방식이 다르다 (D-040)

| 필드 | 방식 | 임계값 반영 | 왜 |
|---|---|---|---|
| `기술영역` | Jaccard | ✅ | 최대 3개 다중값. 완전일치만 보면 2/3 맞춘 것과 0/3 이 같은 점수가 된다 |
| `발표유형` | 정확 일치 | ✅ | 단일값 통제어휘. 맞거나 틀리거나다 |
| `영향도` | 정확=1.0, ±1=0.5 | ✅ | 1~5 **순서형**이다. 2 vs 3 과 2 vs 5 를 같은 오답으로 치면 정보가 사라진다 |
| `관련기업` | Jaccard(canonical) | ❌ 기록만 | 엔티티 경계(오픈소스 프로젝트를 포함할지)가 아직 관찰 중이다 |
| `관련기존기술` | Jaccard | ❌ 기록만 | 자유 태그라 **정답 집합이 닫히지 않는다.** 모델이 더 많이 뽑았다고 틀린 게 아니다 |

비교 전에 `normalize.normalization_key` 로 표기 노이즈를 흡수한다. 정규화가
흡수하는 차이를 채점기가 오답으로 세면, 사전을 고쳐야 할 문제를 모델 탓으로
돌리게 된다.

### 잴 수 없었던 지표는 0 이 아니라 `null` 이다
judge 를 안 돌렸으면 `summary_faithfulness` 는 `null` 이고, 임계값 판정 자체를
하지 않는다. "0점"과 "재지 않았다"를 같은 값으로 쓰면 임계값이 거짓말을 한다.

### judge 실패가 대조 결과를 지우지 않는다
judge 호출이 429 나 스키마 오류로 실패해도 필드 점수는 그대로 남고, 실패 사유가
`errors` 에 기록된다. 요약 채점을 못 했다고 필드 정확도까지 잃을 이유가 없다.

### judge 는 결정적이지 않다 — 그리고 지금은 만들 수 없다
게이트는 `temperature: 0` 으로 판정을 고정했지만(D-032), judge 모델인 Opus 5 는
`temperature` 를 400 으로 거부한다(D-033). **같은 요약을 두 번 채점하면 점수가
갈릴 수 있다.** 추이를 볼 때 1점 차이를 유의미하게 읽으면 안 되고, 이건 골든셋이
쌓인 뒤 재측정으로 폭을 재야 할 항목이다.

> **[2026-09-01 부분 실측]** #33001 을 15회 채점한 결과, **완결성·충실성은
> 변동 0회**, 간결성만 8회 중 2회 갈렸다(4 / 5). 비결정성은 존재하지만
> **가정보다 훨씬 작고 축마다 다르다.** 다만 항목 1건 기준이므로 "judge 는
> 결정적이다"로 뒤집지 않는다 — 이 문단은 유지한다(D-049).

### 루브릭을 v2 로 올렸다 (D-041)
v1 은 `요약` 필드가 생기기 전(D-027)에 쓴 초안이라 간결성 기준이 3~5문장이었다.
스키마는 2~3문장을 요구하므로, **규칙을 지킨 요약이 오히려 감점되는** 구조였다.
출력 형식을 프롬프트에 적어 둔 절도 지웠다 — 스키마는 structured outputs 로
주입되므로(D-009) 프롬프트에 또 적으면 미러가 하나 더 생긴다. v1 은 보존한다.

## 첫 실행 기록 (2026-08-30, D-043)

골든셋 #33001 1건, `claude-opus-5` + `summary_quality.v2.md`, judge 호출 1회.

| 축 | judge | 사람 | 차이 |
|---|---|---|---|
| 충실성 | 4 | 5 | −1 |
| **완결성** | **3** | **1** | **+2** |
| 간결성 | 5 | 5 | 0 |
| 평균 | 4.000 | 3.667 | **`judge_human_gap` +0.333** |

`field_accuracy` 는 0.8333 으로 임계값 0.90 미달(`영향도` 정답 1 vs 모델 2 = 0.5점).
`summary_faithfulness` 는 4.0 으로 임계값 통과.

**이 1건으로 자기 편향 여부를 판단하지 않는다.** 이유가 셋이다.

1. **표본이 1건이다.** 축마다 한 번씩 관측한 것으로는 편향인지 이 기사에 대한
   의견 차이인지 구분할 수 없다.
2. **judge 가 결정적이지 않다**(D-042). Opus 5 는 `temperature` 를 거부해서 같은
   요약을 다시 채점하면 점수가 달라질 수 있다. **`+2` 라는 값 자체가 재현되는지
   확인되지 않았다.**
3. **자기 편향이라면 부호가 반대여야 한다.** 자기 출력에 후한 점수를 주는 것이
   자기 편향인데, 가장 크게 갈린 완결성에서 judge 는 사람보다 **후했다**(3 vs 1) —
   방향은 맞지만, 사람의 1점이 "AI 엔지니어링 직무 관련성" 같은 루브릭 밖 기준을
   일부 반영한 결과라 두 점수가 애초에 같은 것을 재고 있는지가 먼저다.

즉 이 실행이 말해 주는 것은 **"완결성 축에서 사람과 judge 가 갈린다"** 까지이고,
그 원인이 (a) 모델 편향인지 (b) 루브릭이 사람의 기준을 담지 못한 것인지 (c) 단순
샘플링 흔들림인지는 아직 모른다. 골든셋을 늘리고 같은 항목 반복 채점으로 (c) 를
먼저 걷어내야 (a)/(b) 를 가를 수 있다.

### 관찰된 것 — 루브릭 쪽 단서
judge 의 완결성 근거는 "21바이트 재현·영향 범위·Medium 등급이 빠졌다"로, 사람이
`notes` 에 적은 누락 목록(실행 횟수, SIGFPE, Medium 등급, 수정안)과 **상당 부분
겹친다.** 같은 것을 보고도 3점과 1점으로 갈렸다는 뜻이다. v2 루브릭의 완결성
구간이 "하나가 빠졌다=3"까지만 정의돼 있어 **다수 누락을 표현할 칸이 없는 것**이
원인일 수 있다 — 루브릭 v3 을 검토할 때의 1순위 후보다.

### 후속 조치 — 완결성 루브릭 v3 (D-045)

첫 실행 직후 누락 목록을 다시 대조해 보니, **judge 와 사람이 지적한 누락은
합집합 6개 중 1개(`Medium 등급`)만 겹쳤다.**

| judge 가 센 것 | 사람이 센 것 |
|---|---|
| 21바이트 결정론적 재현 | 실행 횟수·소요시간 (495,211회 / 10시간 43분) |
| 연동 애플리케이션 영향 범위 | SIGFPE |
| **Medium 등급** | **Medium 등급** |
| | 수정안 |

**"상당 부분 겹친다"고 본 최초 판단은 틀렸다.** 둘은 같은 누락을 다르게 채점한
것이 아니라 **무엇이 핵심인지에 대해 서로 다른 축을 골랐다** — judge 는 독자
영향(범위·재현성·심각도), 사람은 기술적 detail(발견 비용·신호·수정안). 구간만
촘촘히 나눠서는 해결되지 않는다. 같은 대상을 세게 만들어야 한다.

그래서 v3 은 두 가지를 함께 바꿨다.

1. **핵심 정보를 4슬롯으로 정의** — ①사건 ②범위 ③정도 ④경위. 채점자가 각자
   다른 것을 "핵심"이라 부르면 같은 요약에 다른 점수가 나온다.
2. **슬롯 충족 개수로 구간 세분화** — 4개=5점 … 1개=2점, ①조차 없으면 1점.
   "이름만 언급하고 구체가 없으면 미충족"을 명시했다. 슬롯을 절반만 채운 것을
   충족으로 세면 구간을 나눈 의미가 사라진다.

#33001 에 v3 을 적용하면 ①만 충족(④는 "퍼저가 찾아냈다"로 구체가 없어 미충족)
= **완결성 2점**으로, judge(3)와 사람(1) **사이**에 떨어진다. 어느 한쪽이 옳았다고
보지 않는다 — 슬롯을 고정하면 둘 다 같은 4개를 세게 된다는 것이 요점이다.

> **[2026-09-01 검증 완료]** 위 2점은 작성 당시 루브릭을 손으로 적용한
> 예상치였다. 2026-09-01 반복 실행에서 **8/8 회 모두 2점**으로 재현됐다 —
> 점수뿐 아니라 슬롯 판정(①충족 / ②③④미충족)까지 일치했다. 아래
> "v3 검증 실행" 참고. **원문의 예상치 표현은 지우지 않는다** — 검증 전에
> 무엇을 예상했는지가 남아야 예상이 맞았다는 말에 의미가 생긴다.

**완결성·간결성이 서로 당긴다는 점도 v3 에 명시했다.** 요약은 2~3문장인데(D-027)
슬롯은 4개다. 분량을 지키느라 슬롯을 버린 것은 완결성 감점이 맞고, 두 축을 따로
매기되 한쪽을 위해 다른 쪽을 봐주지 않는다. 이 긴장이 구조적으로 완결성 5점을
어렵게 만드는지는 골든셋이 쌓인 뒤 분포로 확인한다.

### 비용 실측
| 항목 | 값 |
|---|---|
| 입력 | 4,838 토큰 → $0.0242 |
| 출력 | 1,078 토큰 (thinking 639 포함) → $0.0270 |
| **합계** | **$0.0511** |
| 지연 | 18.6초 |
| 캐시 읽기 | 0 |

사전 추정은 $0.03~0.05 였고 실제는 **$0.0511** 로 상단을 조금 넘었다. 어긋난 곳은
입력이다 — 3,200 토큰으로 봤는데 4,838 이 나왔다. 한국어 토큰 밀도를 1.3자/토큰으로
잡은 것이 낙관적이었고(실측 약 0.79자/토큰), structured output 스키마 주입분도
과소평가했다. **다음 추정부터는 한국어를 0.8자/토큰으로 잡는다.**

`cache_read=0` 이라 프롬프트 캐싱(D-019)은 여기서도 미적용이다. judge system
프롬프트 1,212자는 매 호출 동일하므로, 골든셋이 30건이 되면 캐싱 효과가 나온다.

## v3 검증 실행 (2026-09-01, D-048)

골든셋 #33001 1건, `claude-opus-5`. **루브릭 2개를 팔로 나눠** 반복 채점했다.

| 팔 | 루브릭 | 호출 | 역할 |
|---|---|---|---|
| A | `summary_quality.v3.md` | 10회 (성공 8) | 검증 대상 |
| B | `summary_quality.v2.md` | 5회 (성공 5) | **대조군** |

**대조군을 함께 돌린 이유.** v3 가 2 를 내더라도, v2 쪽 표본이 1건(D-043)뿐이면
"v3 가 점수를 옮겼다"와 "judge 가 원래 2~3 을 오가는데 우연히 3 을 뽑았다"를
구분할 수 없다. 대조군 없이 v3 만 반복하는 것은 D-043 이 경계한 오류를 한 층
위로 옮기는 것에 지나지 않는다.

### 사전 등록 기준과 판정

가설과 임계값을 **데이터를 보기 전에** 고정했다. 실행 후에 정하면 어떤 결과가
나와도 성공으로 읽을 수 있다.

| 가설 | 기준 | 실측 | 판정 |
|---|---|---|---|
| H1 중심 이동 | 최빈값=2 ∧ 비율≥0.6 ∧ spread≤1 | 최빈값 2, 비율 8/8, spread 0 | **수렴** |
| H2 흔들림 감소 | `sd(v3) < sd(v2)` | 0.0 vs 0.0 | **판정 불가** |
| H3 루브릭 준수 | `slot_adherence ≥ 0.8` | 1.0 | **통과** |

**H2 는 기각된 것이 아니라 전제가 틀렸다.** v2 도 완결성에서 5회 전부 3점,
`sd=0` 이었다 — 줄일 흔들림이 애초에 없었다.

### 완결성 분포

| | n | 분포 | mean | sd | range |
|---|---|---|---|---|---|
| **v3** | 8 | `{2: 8}` | **2.0** | 0.0 | 2–2 |
| **v2** | 5 | `{3: 5}` | **3.0** | 0.0 | 3–3 |
| 사람 | 1 | — | 1 | — | — |

`judge_human_gap` 은 **+0.333 → −0.083**, 완결성 축만 보면 **+2.0 → +1.0** 이다.
부수적으로 v2 5회가 D-043 의 단발 기록(4 / 3 / 5, gap +0.333)을 그대로 재현했다.

### 점수가 아니라 근거가 일치했다

`slot_fill_rate` — 8회 전부 **같은 슬롯을 같은 이유로** 판정했다.

| 슬롯 | v3 충족률 | 손계산 예상 |
|---|---|---|
| ① 사건 | 1.00 | 충족 |
| ② 범위 | 0.00 | 미충족 |
| ③ 정도 | 0.00 | 미충족 |
| ④ 경위 | 0.00 | 미충족 (이름만 언급) |

특히 ④ 는 8회 모두 "'퍼저가 찾아냈다'는 이름만 언급이고 495,211회·10시간 43분이
빠졌다"로 적었다 — v3 가 새로 넣은 **"이름만 언급하면 미충족"** 규칙이 실제로
작동한 지점이다. 점수만 맞은 것이 아니라 판정 경로가 일치했으므로, 2점이 우연히
나온 값이 아니다.

### 측정 도구가 먼저 틀렸다

첫 집계에서 `slot_adherence` 가 **0.5** 로 나왔다. 근거 8개는 전부 4슬롯을
열거했고, **틀린 것은 파서였다.** 판정어 탐색 창을 마커 뒤 60자로 고정했는데,
모델은 괄호에 근거를 길게 달고 판정어를 맨 뒤에 둔다.

```
②범위(avformat_open_input·av_read_frame 을 신뢰할 수 없는 데이터에
호출하는 모든 FFmpeg 연동 애플리케이션) 미충족
                                        ^^^ 창 밖 -> "언급 없음" 으로 오독
```

다음 슬롯 마커 또는 총계 화살표(`→`)까지로 고치고 **저장된 결과를 재집계**해
1.0 을 얻었다. **API 재호출은 없었다** — 집계를 순수 함수로 분리해 둔 값이
여기서 나왔다(`eval/analysis.py`). 실제 근거 문자열로 회귀 테스트를 남겼다.

`eval/scores/20260901T093244Z.jsonl` 의 `summary` 줄에는 수정 전 값(0.5)이 남아
있다. `item` 줄이 원자료이고 집계는 파생물이므로, 파일을 고치지 않고 재집계로
바로잡는다.

### judge 호출 실패 2건 (10회 중)

모델 거부가 아니라 **응답 파편화**다. `rationale` 이 `'f'`, `'2
dp'`,
`'fe6'` 같은 조각으로 와서 `min_length=5` 검증에 걸렸다. 내용이 짧은 것이
아니라 깨진 것이므로 스트리밍 조립 쪽 문제로 보이고, 원인 추적은 별도 항목이다.
"judge 실패가 대조 결과를 지우지 않는다"는 설계대로 나머지 8회는 온전히 남았다.

**부작용**: 실패한 호출은 `judge_usage` 가 `None` 이라 사용량이 기록되지 않는데
**API 는 이미 응답했으므로 과금은 된다.** 비용 기록에 구멍이 있다(D-051).

## 골든셋 2건 실행 (2026-09-01, D-053)

2번째 항목 `20260831-arxiv-2608.31100-s3gym` 을 확정하고 2건을 함께 채점했다.
`summary_quality.v3.md`, 항목당 1회.

|---|---|---|
| 충실성 | judge 4 / 사람 **5** | **5 / 5** |
| 완결성 | judge 2 / 사람 **1** | **5 / 5** |
| 간결성 | 5 / 5 | **5 / 5** |
| `judge_human_gap` | 0.0 | **0.0** |

집계: `field_accuracy` **0.8611**(임계값 0.90 미달), `summary_faithfulness`
**4.5**(통과). 비용 $0.1070(입력 12,144 / 출력 1,851 토큰), 지연 합계 31.5초.

### 사람과 judge 가 처음으로 같은 눈금을 썼다

S3Gym 은 **v3 4슬롯 기준으로 사람이 라벨링한 첫 항목**이다(#33001 은
`pre-2026-08-30`). 결과는 세 축 모두 일치했고, 슬롯 판정도 ①②③④ 전부 충족으로
같았다. 특히 judge 는 ③정도에서 "원문이 수치를 제시하지 않고 정성적 결과만
제공"한다며 **원문이 주지 않은 정보를 분모에서 빼는 규칙**을 스스로 적용했다 —
v3 가 넣은 규칙이 설계대로 작동한 두 번째 지점이다(첫 번째는 "이름만 언급하면
미충족").

**이것으로 자기 편향이 없다고 말할 수는 없다.** 두 점수가 같다는 것은 **같은
눈금을 쓰면 갈리지 않는다**는 뜻이고, 편향이 있다면 눈금이 같아도 남는다. 항목이
2건이고 그중 사람이 v3 기준으로 매긴 것은 1건이다.

### `judge_human_gap` 이 상쇄를 숨긴다

#33001 의 gap 은 0.0 이지만 축별로는 **충실성 −1, 완결성 +1, 간결성 0** 이다.
반대 방향 오차가 상쇄돼 평균이 0 이 된 것이고, 두 축에서는 여전히 갈린다.

**평균의 평균을 자기 편향 지표로 쓰면 이 상쇄가 보이지 않는다.** 축별 gap 을
함께 봐야 하고, `RepeatStats.gap(axis)` 가 이미 축별로 계산한다. 종합 gap 만
읽으면 "일치했다"는 잘못된 결론이 나온다.

### 한 필드가 전체를 좌우하는 문제는 완화됐을 뿐이다

| 필드 | #33001 | S3Gym |
|---|---|---|
| 기술영역 | 1.000 | **0.667** (사람이 `Training/Finetuning` 제외) |
| 발표유형 | 1.000 | 1.000 |
| 영향도 | **0.500** (절대오차 1) | **1.000** |
| 항목 평균 | 0.8333 | 0.8889 |

필드 1개의 최대 영향은 0.333 에서 **0.167** 로 절반이 됐다. 그러나 임계값
0.90 까지 거리가 **0.039** 뿐이라 **어느 한 필드가 만점이 되기만 해도 판정이
뒤집힌다** — #33001 영향도가 1.0 이면 0.9444, S3Gym 기술영역이 1.0 이면 0.9167.

**"해소됐다"가 아니라 "레버리지가 절반이 됐다"가 정확한 표현이다.** 다만 두
항목이 **서로 다른 필드에서** 감점된 것은 골든셋으로서 좋은 신호다 — 같은
필드에서만 틀렸다면 2건이어도 한 축만 재는 셈이다.

`관련기업`·`관련기존기술` 은 양쪽 1.000 이지만 `기록만` 이다. S3Gym 은 정답과
출력이 모두 빈 목록이라 Jaccard 가 1.0 인데, 이건 "완벽히 맞혔다"가 아니라
**빈 집합끼리의 일치**다.

## 판정 기준 (config.yaml: eval.thresholds)
- 통제어휘 필드 정확도 ≥ 0.90
- 요약 충실성 평균 ≥ 4.0

초안값이다. 골든셋 30건 이상 쌓인 뒤 실측으로 재조정한다.

## Judge 편향에 대한 메모
judge 와 extractor 가 같은 모델이면 자기 출력에 후한 점수를 줄 수 있다.
골든셋에 **사람 점수**를 함께 저장해 judge–사람 일치도를 주기적으로 확인하고,
일치도가 낮아지면 루브릭을 고친다. judge 점수 자체도 검증 대상이다.

채점 결과의 `judge_human_gap` 이 그 지표다(= judge 평균 − 사람 평균). 사람 점수가
없으면 이 값은 `null` 이고 `errors` 에 "자기 편향을 확인할 수 없다"가 남는다 —
**편향이 없다는 뜻이 아니라 재지 못했다는 뜻이다.** 그래서 골든셋을 확정할 때
`human_summary_scores` 를 함께 채우는 것이 권장된다.

judge 모델을 extractor 와 다른 모델로 바꿀지는 실행 결과를 보고 정하기로 이미
합의돼 있다. 지금은 `eval.judge_model` 을 그대로 쓴다.
